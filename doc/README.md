# NMX-1108 RS-232C 브리지 스니퍼

NTU **NMX-1108** 8채널 영상믹서의 본체와 전용 컨트롤러 **사이에 ESP32를 끼워 넣어**,
양방향 데이터를 그대로 중계하면서 오가는 RS-232C 프로토콜을 해석·기록한다.

최종 목표는 프로토콜을 완전히 파악한 뒤, **PC 또는 네트워크를 통해 믹서를 제어하는
대체 컨트롤러**를 만드는 것이다. 지금 단계는 그 전제가 되는 프로토콜 관찰이다.

NMX-1108의 공식 프로토콜 자료는 없다. 6채널 모델인 **NMX-1106 프로토콜 문서**를 기준으로
해석하고, NMX-1108에서 확장된 부분(CH7/CH8 등)은 미확인이므로 로그에 `?` 를 붙여 구분한다.

> **중계 방식의 전제**
> 원래 컨트롤러-본체를 잇던 케이블을 제거하고 ESP32가 그 자리를 대신한다.
> 따라서 **ESP32의 전원이 끊기거나 펌웨어가 리셋되면 믹서 조작도 함께 멈춘다.**
> 실사용 중인 장비라면 원래 케이블을 옆에 두고 바로 되돌릴 수 있게 준비해 둔다.

## 2. 하드웨어

### 2.1 배선

ESP32가 두 장비 사이의 통로가 된다. 각 방향마다 MAX3232를 하나씩 쓰고,
**RX와 TX를 모두** 연결한다.

> **먼저 짚어둘 것.** 아래 그림에서 `┊ 펌웨어 ┊` 로 이어진 부분은 **전선이 아니다.**
> ESP32가 한쪽 UART에서 읽은 바이트를 다른 쪽 UART로 써 보내는 **소프트웨어 동작**이다.
> GPIO 핀끼리는 절대 직접 연결하지 않는다.

**방향 ①  컨트롤러 → 본체**

```text
  [컨트롤러] TxD ──► R1IN [MAX3232 #1] R1OUT ──► GPIO16  (Serial1 RX)
                                                    ┊
                                                    ┊  펌웨어가 읽어서 그대로 write
                                                    ▼
  [본체]     RxD ◄── T1OUT [MAX3232 #2] T1IN ◄── GPIO27  (Serial2 TX)
```

**방향 ②  본체 → 컨트롤러**

```text
  [본체]     TxD ──► R1IN [MAX3232 #2] R1OUT ──► GPIO26  (Serial2 RX)
                                                    ┊
                                                    ┊  펌웨어가 읽어서 그대로 write
                                                    ▼
  [컨트롤러] RxD ◄── T1OUT [MAX3232 #1] T1IN ◄── GPIO17  (Serial1 TX)
```

**GND** 는 컨트롤러 / MAX3232 #1 / ESP32 / MAX3232 #2 / 본체를 모두 하나로 묶는다.

### 실제로 연결하는 선 (총 4가닥 + GND)

각 GPIO는 MAX3232의 핀 **하나**에만 붙는다. GPIO끼리 이어지는 선은 없다.

| # | ESP32 핀 | 성격 | 연결 상대 |
|---|---|---|---|
| 1 | GPIO16 `Serial1 RX` | 입력 | MAX3232 **#1** 의 TTL 출력 (R1OUT) |
| 2 | GPIO17 `Serial1 TX` | 출력 | MAX3232 **#1** 의 TTL 입력 (T1IN) |
| 3 | GPIO26 `Serial2 RX` | 입력 | MAX3232 **#2** 의 TTL 출력 (R1OUT) |
| 4 | GPIO27 `Serial2 TX` | 출력 | MAX3232 **#2** 의 TTL 입력 (T1IN) |

- MAX3232 **#1** 은 컨트롤러 쪽, **#2** 는 본체 쪽 전담이다. 한 모듈이 양쪽 장비에 걸치지 않는다.
- **GPIO16↔GPIO27, GPIO26↔GPIO17 을 직접 연결하면 안 된다.** MAX3232의 출력과 ESP32의
  출력이 같은 선을 서로 구동해 소자가 상할 수 있고, 신호가 ESP32를 거치지 않고 흘러버린다.
- MAX3232 모듈의 TTL 쪽 핀 라벨은 제품마다 `TXD`/`RXD` 로 적혀 있어 방향이 헷갈린다.
  **칩 기준으로 `T1IN` 은 입력(ESP32 TX가 물림), `R1OUT` 은 출력(ESP32 RX가 물림)** 이라는
  것만 기억하고, 모듈 실크가 애매하면 테스터로 확인한다.

핀 번호는 [../src/main.cpp](../src/main.cpp) 상단의 `CTRL_RX_PIN` 등에서 바꾸거나,
[../platformio.ini](../platformio.ini) 의 `build_flags` 에서 `-DCTRL_RX_PIN=...` 로 덮어쓴다.
현재 설정은 `pins` 명령으로 확인한다.

### 2.2 RJ45 핀어사인

NMX-1106 자료 기준 RS-232C 포트는 다음과 같다.

| RJ45 핀 | RS-232C 신호 |
|---:|---|
| 4번 | GND |
| 5번 | RxD |
| 6번 | TxD |

**이 표기는 장비 포트 기준일 가능성이 높다.** 즉 장비의 `RxD` 는 장비가 받는 선이므로,
ESP32 입장에서는 송신해야 할 선이다. 연결 전에 방향을 확인한다.
중계 방식에서는 방향을 틀리면 믹서가 아예 동작하지 않으므로 판별은 오히려 쉽다
([ToDo.md](ToDo.md) A-2).

### 2.3 안전 요구사항

1. RS-232C는 ±전압을 쓰므로 ESP32 GPIO에 **직접 연결하지 않는다.** MAX3232를 반드시 거친다.
2. GND는 컨트롤러 / MAX3232 ×2 / ESP32 / 본체를 모두 공통으로 묶는다.
3. ESP32 전원은 중계 도중 끊기지 않도록 안정적인 소스를 쓴다.
4. 송신(주입) 기능은 기본 비활성이며 `inject on` 을 거쳐야 동작한다.
5. 원래 케이블을 항상 옆에 두고, 문제가 생기면 즉시 되돌린다.

## 3. 중계 설계

장비 통신을 방해하지 않는 것이 최우선이라, 다음과 같이 구현했다.

1. **바이트 단위 즉시 통과.** 프레임이 모이기를 기다리지 않고 받은 즉시 반대편으로 내보낸다.
   지연은 1바이트분(약 1ms)이고, 파서가 동기를 잃거나 체크섬이 깨져도 중계는 영향받지 않는다.
2. **중계가 로그보다 우선.** 코드 순서상 중계 `write()` 가 먼저 실행된다.
3. **로그가 중계를 막지 않는다.** USB 출력 버퍼에 여유가 없으면 로그 줄을 통째로 버리고
   카운트만 올린다. 버려진 줄 수는 `stats` 의 `dropped log lines` 에 나온다.
4. **부팅 중 글리치 방지.** UART 초기화 전에 TX 핀을 idle(High)로 고정해
   전원 인가 순간 쓰레기 바이트가 실리지 않게 한다.

`stats` 에서 `bytes` 와 `relayed` 가 같으면 한 바이트도 빠뜨리지 않고 넘긴 것이다.

## 4. 출력 형식

```text
[CTRL->MAIN] 00:00:12.345  AB 09 00 00 01 4A  CHK=OK   PGM CH 1
[CTRL->MAIN] 00:00:12.902  AB 0B 00 00 02 47  CHK=OK   NEXT CH 2
[MAIN->CTRL] 00:00:13.010  AA D2 55 01 02 2A  CHK=OK   STATUS PGM=CH1 PVW=CH2
[MAIN->CTRL] 00:00:13.300  AA D3 55 02 04 7C  CHK=BAD  STATUS EFFECT=1 INV=OFF ...  [expected CHK=26]
```

`CTRL->MAIN` 은 컨트롤러가 보내 본체로 넘긴 것, `MAIN->CTRL` 은 그 반대다.
타임스탬프는 `millis()` 기반의 `HH:MM:SS.mmm` 이다.

프레임 외의 상황도 버리지 않고 남긴다.

| 표시 | 의미 |
|---|---|
| `RAW  ...` | `raw on` 모드의 원시 바이트 |
| `SKIP n byte(s): ...` | 헤더(`AB`/`AA`) 이전에 들어온 바이트 |
| `INCOMPLETE (n/6 bytes, timeout)` | 6바이트가 채워지기 전에 50ms 이상 끊긴 프레임 |
| `RESYNC from offset n` | 체크섬 불일치 후 프레임 내부 헤더에서 동기 재획득 |

체크섬이 틀려도 프레임은 반드시 출력하며, 알 수 없는 CMD도 `UNKNOWN CMD 0xNN` 으로 남는다.
이 모든 판정은 **관찰용일 뿐이고 중계에는 영향을 주지 않는다.**

### 파서 동작

- `0xAB` 또는 `0xAA` 가 들어오면 프레임 수집을 시작하고, 6바이트가 차면 처리한다.
- **체크섬이 틀렸을 때만** 프레임 내부의 헤더 바이트에서 동기를 다시 잡는다.
  데이터에 `0xAB` 가 실릴 수 있어(페이더 값 등) 무조건 재동기하면 정상 프레임이 깨지기 때문이다.
- 프레임 길이는 6바이트 고정으로 가정한다 (검증은 [ToDo.md](ToDo.md) A-4).

## 5. 시리얼 명령

| 명령 | 기능 |
|---|---|
| `help` | 명령 목록 |
| `relay on` / `relay off` | 양방향 중계 (기본 **on**) |
| `raw on` / `raw off` | 원시 바이트 HEX 출력 |
| `frame on` / `frame off` | 프레임 파서 출력 (기본 on) |
| `stats` | 방향별 바이트/중계/프레임/체크섬 통계 |
| `clear` | 통계 초기화 |
| `pins` | 현재 UART 핀·보레이트 |
| `selftest` | 문서 예제 47개로 디코더 검증 |
| `inject on` / `inject off` | 임의 프레임 송신 허용 (기본 **off**) |
| `sendmain <hex...>` | 본체로 송신. 5바이트만 주면 체크섬 자동 계산 |
| `sendctrl <hex...>` | 컨트롤러로 송신 |

`relay off` 는 컨트롤러 명령이 본체에 닿지 않게 막는다. 어떤 동작이 컨트롤러에서
나온 것인지 확인할 때 쓰지만, **그동안 믹서 조작은 먹지 않는다.**

`sendmain` / `sendctrl` 은 중계 트래픽 사이에 임의 프레임을 끼워 넣는다.
프로토콜을 확인한 뒤에 쓰고, `inject on` 을 거쳐야 나간다.

```text
> inject on
> sendmain AB D2 00 00 01        ← 체크섬 자동 계산 (81)
TX ->MAIN: AB D2 00 00 01 81  CHK=OK   STATUS REQ PGM/PVW
```

> `stats` 같은 긴 출력은 잠깐(수십 ms) 중계를 지연시킬 수 있다. 데이터가 유실되지는
> 않지만(RX 버퍼 512바이트), 조작이 몰리는 중에는 피하는 편이 좋다.

# 2부. 프로토콜

## 7. 프레임 구조

6바이트 고정 길이. 요청/제어는 `AB`, 응답은 `AA` 로 시작한다.

```text
요청  AB CMD D1 D2 D3 CHK
응답  AA CMD D1 D2 D3 CHK

CHK = (0x54 - CMD - D1 - D2 - D3) & 0xFF
```

체크섬 식은 **원문 문서의 예제 프레임 78개 전부와 일치**하는 것을 확인했다.

```cpp
uint8_t nmxChecksum(const uint8_t frame[6]) {
    return static_cast<uint8_t>(0x54 - frame[1] - frame[2] - frame[3] - frame[4]);
}
```

## 8. 명령표

CMD 요약이다. 상세 값은 8.1 이하에 있다.

| CMD | 의미 |
|---:|---|
| `0x01` | SETUP key |
| `0x02` | Audio Select EXT |
| `0x05` | Effect Number / Effect INV |
| `0x06` | Fader Mode CUT/TAKE |
| `0x07` | Manual Fader value (`D2:D3` 16비트) |
| `0x08` | PGM overlay CKEY/DSK/PIP 비트마스크 |
| `0x09` | PGM CH |
| `0x0B` | NEXT/PVW CH |
| `0xD0` | Default |
| `0xD2` | PGM/PVW 상태 요청·응답 |
| `0xD3` | EFFECT/CKEY/PIP/DSK/AUDIO 상태 요청·응답 |

### 8.1 SETUP (`0x01`)

```text
AB 01 00 00 06 4D   SETUP ENTER (MENU)
AB 01 00 00 08 4B   SETUP ESC
AB 01 00 00 01 52   SETUP UP?      ← 원문 한글 깨짐. 추정
AB 01 00 00 00 53   SETUP DOWN?    ← 원문 한글 깨짐. 추정
AB 01 00 00 03 50   SETUP LEFT     (sub menu -)
AB 01 00 00 02 51   SETUP RIGHT    (sub menu +)
```

### 8.2 Audio Select EXT (`0x02`)

```text
AB 02 00 00 00 52   EXT OFF
AB 02 00 00 01 51   EXT ON
```

### 8.3 EFFECT (`0x05`)

`D3` 의 하위 니블이 번호, `0x10` 비트가 INV 플래그다.

```text
AB 05 00 00 01 4E   EFFECT 1 (좌우)      AB 05 00 00 11 3E   EFFECT 1 INV
AB 05 00 00 02 4D   EFFECT 2 (상하)      AB 05 00 00 12 3D   EFFECT 2 INV
AB 05 00 00 03 4C   EFFECT 3             AB 05 00 00 13 3C   EFFECT 3 INV
AB 05 00 00 04 4B   EFFECT 4             AB 05 00 00 14 3B   EFFECT 4 INV
AB 05 00 00 05 4A   EFFECT 5             AB 05 00 00 15 3A   EFFECT 5 INV
AB 05 00 00 06 49   EFFECT 6             AB 05 00 00 16 39   EFFECT 6 INV
AB 05 00 00 07 48   EFFECT 7 (FOUT/IN)   AB 05 00 00 17 38   EFFECT 7 INV
AB 05 00 00 08 47   EFFECT 8 (MIX)       AB 05 00 00 18 37   EFFECT 8 INV
```

### 8.4 FADER MODE (`0x06`) / FADER 값 (`0x07`)

```text
AB 06 00 00 01 4D   FADER MODE TAKE
AB 06 00 00 02 4C   FADER MODE CUT

AB 07 00 00 00 4D   FADER OFF
AB 07 00 00 11 3C   값 0x011
AB 07 00 00 FF 4E   값 0x0FF
AB 07 00 01 00 4C   값 0x100
AB 07 00 01 FF 4D   값 0x1FF
```

`0x07` 은 `D2:D3` 를 16비트로 합친 값이 페이더 위치다. 원문 예제 범위는 `0x000`~`0x1FF`.

### 8.5 PGM 오버레이 (`0x08`)

`D3` 가 비트마스크다. bit0=CKEY, bit1=DSK, bit2=PIP.

```text
AB 08 00 00 00 4C   ALL OFF
AB 08 00 00 01 4B   CKEY
AB 08 00 00 02 4A   DSK
AB 08 00 00 04 48   PIP
AB 08 00 00 03 49   DSK + CKEY
AB 08 00 00 05 47   PIP + CKEY
AB 08 00 00 06 46   PIP + DSK
AB 08 00 00 07 45   ALL ON
```

### 8.6 PGM CH (`0x09`) / NEXT·PVW CH (`0x0B`)

`D3` 에 채널 번호가 그대로 실린다.

```text
AB 09 00 00 00 4B   PGM CH OFF      AB 0B 00 00 00 49   NEXT CH OFF
AB 09 00 00 01 4A   PGM CH1         AB 0B 00 00 01 48   NEXT CH1
AB 09 00 00 02 49   PGM CH2         AB 0B 00 00 02 47   NEXT CH2
AB 09 00 00 03 48   PGM CH3         AB 0B 00 00 03 46   NEXT CH3
AB 09 00 00 04 47   PGM CH4         AB 0B 00 00 04 45   NEXT CH4
AB 09 00 00 05 46   PGM CH5         AB 0B 00 00 05 44   NEXT CH5
AB 09 00 00 06 45   PGM CH6         AB 0B 00 00 06 43   NEXT CH6
```

NMX-1108 확장 **추정값** (실측 필요, [ToDo.md](ToDo.md) B-1·B-2):

```text
AB 09 00 00 07 44   PGM CH7?        AB 0B 00 00 07 42   NEXT CH7?
AB 09 00 00 08 43   PGM CH8?        AB 0B 00 00 08 41   NEXT CH8?
```

### 8.7 Default (`0xD0`)

```text
AB D0 00 00 01 83   Default
```

### 8.8 상태 조회 (`0xD2`, `0xD3`)

```text
AB D2 00 00 01 81   요청: PGM CH, PVW CH
AA D2 55 01 02 2A   응답 예: PGM=CH1, PVW=CH2

AB D3 00 00 01 80   요청: EFFECT, CKEY/PIP/DSK/AUDIO
AA D3 55 xx xx --   응답
```

응답의 3번째 바이트는 `0x55` 고정으로 보인다.

**`D2` 응답 — 채널 비트마스크** (4번째=PGM, 5번째=PVW)

| 값 | 의미 |
|---:|---|
| `0x01` | CH1 |
| `0x02` | CH2 |
| `0x04` | CH3 |
| `0x08` | CH4 |
| `0x10` | CH5 |
| `0x20` | CH6 |
| `0x40` | **OFF** (NMX-1106 기준) |

NMX-1108에서 CH7/CH8이 들어갈 자리인 `0x40` 을 이미 OFF가 쓰고 있다.
**OFF 코드가 바뀌었거나 CH7/CH8이 다른 방식으로 실린다는 뜻**이므로 실측이 필요하다
([ToDo.md](ToDo.md) B-3).

**`D3` 응답 — 상태 비트**

4번째 바이트:

| 비트 | 의미 |
|---|---|
| bit0 | EFFECT INV |
| bit1~bit7 | EFFECT 1 ~ EFFECT 7 |

5번째 바이트:

| 비트 | 의미 |
|---|---|
| bit0 | EFFECT 8 |
| bit1 | CG |
| bit2 | PIP |
| bit3 | DSK |
| bit4, bit5 | Fixed 0 |
| bit6 | EXT AUDIO |
| bit7 | Fixed 0 |

## 9. NMX-1108에서 확인해야 할 것

NMX-1108 확장분은 아직 추정이라, 펌웨어가 해당 구간을 로그에 `?` 로 표시한다.

| 로그 표시 | 뜻 |
|---|---|
| `PGM CH 7?` / `NEXT CH 8?` | 채널 명령이 NMX-1106 규칙의 연장인지 미확인 |
| `PGM=OFF\|CH7?` | `D2` 응답의 `0x40` 이 OFF인지 CH7 비트인지 미확인 |
| `CH8?` | `0x80` 을 CH8로 가정 |
| `fixed-0 bits set: 0x..?` | 문서상 0이어야 할 비트가 켜짐. 8채널 확장 신호일 수 있음 |
| `UNKNOWN CMD 0xNN` | NMX-1106 문서에 없는 명령 |

항목별 테스트 절차와 판정 기준은 **[ToDo.md](ToDo.md)** 에 정리해 두었다.
플래시 직후 `selftest` → 배선/중계 확인(A-2) → 8N1 확인(A-3) 순으로 진행한다.

프로토콜이 예상과 완전히 다르면 `raw on` 으로 전환해 원시 바이트부터 관찰한다.

# 3부. [설계안] v3 — UART0 메뉴 시스템

> **미구현. 검토용이다.** 아래 내용은 아직 코드에 반영하지 않았다.
> 확정되면 그때 구현한다.

## 10. 배경과 범위

지금은 `raw on` 같은 텍스트 명령을 외워서 쳐야 하고, 핀·보레이트를 바꾸려면 재빌드해야 하며,
설정은 재부팅하면 사라진다. 또 프로토콜 분석에 정작 필요한 정보 — 어떤 CMD가 몇 번 왔는지,
해석 못 한 패킷이 무엇이었는지 — 는 흘러가는 로그를 눈으로 훑어야 찾을 수 있다.

| 포함 | 제외 (v4 이후) |
|---|---|
| UART0 메뉴 UI | 네트워크로 **프레임 주입** |
| 설정 **변경 즉시** Flash 저장 | WebSocket 실시간 스트림 |
| UART 핀·보레이트·프레임형식 런타임 변경 | OTA 업데이트 |
| WiFi **AP / STA / AP+STA 동시** | SD 카드 로깅 |
| **웹 UI** — 메뉴와 같은 기능을 브라우저로 | 스탠드얼론 컨트롤러 모드 |
| RAW 뷰 / Unresolved 버퍼 / 패킷 통계 | |
| Factory reset | |

WiFi와 웹 UI를 v3에 넣는 이유는, 최종 목표인 **네트워크 제어 디바이스**로 가기 전에
무선과 HTTP 처리가 중계에 지장을 주지 않는지 먼저 확인해 두기 위해서다.
웹에서 **읽고 설정하는 것까지가 v3**이고, 웹에서 장비로 **프레임을 쏘는 것은 v4**다.

> **이 추가가 부르는 구조 변경.** 웹 서버가 들어오면 `loop()` 폴링만으로는
> 중계 지연을 감당하기 어렵다. v3에서 **중계를 전용 FreeRTOS 태스크로 분리**한다.
> 자세한 내용은 17장에 있다.

## 11. 동작 모드

UART0 하나로 로그와 메뉴를 같이 쓸 수 없으므로 모드를 나눈다.

| 모드 | 화면 | 진입 |
|---|---|---|
| **모니터 모드** (기본) | 프레임/RAW 로그가 계속 흐른다. 기존 텍스트 명령도 그대로 동작 | `ESC` 또는 `0` + Enter |
| **메뉴 모드** | 로그 출력 중단, 메뉴 UI 표시 | `ESC` 또는 빈 줄에서 Enter |

**두 모드 모두에서 중계는 멈추지 않는다.** 메뉴 모드에서도 수집은 계속되므로,
메뉴를 보는 동안 지나간 패킷도 Unresolved 버퍼와 통계에는 그대로 반영된다.
화면에 안 뿌릴 뿐이다.

기존 텍스트 명령(`stats`, `raw on` …)은 없애지 않는다. 메뉴보다 빠르고 로그로 남기기 좋다.

## 12. 메뉴 트리

```text
메인
├─ 1) Network 설정
│    ├─ 1-1) 무선 모드 (OFF / STA / AP / AP+STA)
│    ├─ 1-2) AP 설정
│    │        ├─ AP 이름(SSID)     기본값 NMX1108_SNIFFER
│    │        ├─ AP 비밀번호
│    │        ├─ AP 채널

│    ├─ 1-3) STA 설정

│    │        ├─ 비밀번호

│    ├─ 1-4) 호스트명             기본값 nmx-bridge
│    ├─ 1-5) 웹 UI (on / off, 포트)
│    └─ 1-6) 지금 연결 / 끊기 · 현재 상태
├─ 2) UART 설정
│    ├─ UART1 (컨트롤러측) RX·TX 핀 / Baud / Format
│    ├─ UART2 (본체측)     RX·TX 핀 / Baud / Format
│    ├─ 양쪽 동일하게 적용
│    └─ 되돌리기 (30초 확인)
├─ 3) Debug / Monitor
│    ├─ 3-1) RAW 스트림 보기
│    ├─ 3-2) Unresolved 패킷 (최근 10개)
│    ├─ 3-3) 패킷 상태 / 통계
│    ├─ 3-4) 디코딩 로그 설정
│    ├─ 3-5) 중계 제어 (relay on/off)
│    ├─ 3-6) 프레임 주입 (inject / sendmain / sendctrl)
│    └─ 3-7) 디코더 selftest
├─ 4) System
│    ├─ 4-1) 설정 텍스트로 덤프
│    ├─ 4-2) 장치 정보 (버전 / uptime / free heap / 리셋 사유)
│    ├─ 4-3) 재부팅
│    └─ 4-4) Factory reset  ← 모든 설정을 공장 기본값으로
```

조작은 **숫자 키 + Enter** 방식으로 한다. 화살표 키(ANSI 이스케이프)는
`pio device monitor` 나 다른 터미널에서 동작이 제각각이고 `ESC` 키와 충돌하기 때문이다.
화면 지우기 정도만 ANSI를 쓰고, 이것도 설정에서 끌 수 있게 한다.

**"저장" 메뉴가 없다.** 모든 설정은 값을 확정하는 즉시 Flash에 기록된다(16장).
System 메뉴에 있던 `설정 저장 / 불러오기` 항목은 그래서 사라졌다.

머리말에 현재 상태를 항상 띄워서, 메뉴를 돌아다니는 중에도
중계가 살아 있는지 한눈에 보이게 한다.

### 13.2 UART 설정

```text
--- UART 설정 -------------------------------------------
              UART1 (컨트롤러측)   UART2 (본체측)
   RX 핀        GPIO16               GPIO26
   TX 핀        GPIO17               GPIO27
   Baud          9600                 9600
   Format         8N1                  8N1
---------------------------------------------------------
  1) UART1 RX 핀      5) UART2 RX 핀
  2) UART1 TX 핀      6) UART2 TX 핀
  3) UART1 Baud       7) UART2 Baud
  4) UART1 Format     8) UART2 Format
  9) 양쪽 동일하게 맞추기

  r) 되돌리기 (직전 값으로)
  0) 뒤로
>
```

**핀 입력 검증** — 잘못된 핀을 넣으면 중계가 죽거나 보드가 부팅되지 않으므로,
입력 즉시 거른다.

| 핀 | 판정 |
|---|---|
| 1, 3 | **거부.** UART0(이 콘솔)이 쓰는 핀 |
| 6 ~ 11 | **거부.** SPI 플래시 전용 |
| 34 ~ 39 | RX만 허용. 입력 전용이라 **TX 불가** |
| 0, 2, 5, 12, 15 | 경고 후 허용. 부팅 스트래핑 핀 |
| 16, 17 | 경고 후 허용. **PSRAM 탑재 보드(WROVER)에서는 사용 불가** |
| 그 외 | 허용 |

두 UART가 같은 핀을 쓰거나, RX와 TX가 겹치면 거부한다.

**Baud** 2400 / 4800 / **9600** / 19200 / 38400 / 57600 / 115200
**Format** **8N1** / 8E1 / 8O1 / 7E1 / 7O1 — [ToDo.md](ToDo.md) A-3(패리티 확정) 검증을 재빌드 없이 할 수 있게 된다.

**되돌리기 안전장치** — UART 설정만은 즉시 저장에 예외를 둔다.
잘못 바꾸면 장비 통신이 끊기는데, 그 값이 그대로 Flash에 굳으면 재부팅해도 끊긴 채로 뜬다.

그래서 UART 설정은 이렇게 동작한다.

1. 값을 바꾸면 **즉시 적용하고, 새 값과 직전 값을 함께 Flash에 기록**한다.
2. 화면에 `30초 안에 확인하지 않으면 되돌립니다` 카운트다운이 뜬다.
3. 아무 키나 눌러 확인하면 확정, 확인이 없으면 **직전 값으로 자동 복구하고 그것도 Flash에 기록**한다.

이렇게 하면 어느 시점에 전원이 나가도 Flash에는 항상 "동작하던 설정"이 남는다.
UART0 콘솔은 115200 고정이고 GPIO 1·3은 설정에서 거부되므로, **최악의 경우에도 메뉴는 살아 있다.**

### 13.3 Network 설정

```text
--- Network 설정 ----------------------------------------
   무선 모드   AP+STA
   AP  SSID    NMX1108_SNIFFER   상태  동작중  접속 1대
       IP      192.168.4.1       채널  6
   STA SSID    MyAccessPoint     상태  연결됨
       IP      192.168.0.42      RSSI  -58 dBm
   호스트명    nmx-bridge        웹 UI on (:80)
---------------------------------------------------------
  1) 무선 모드 (OFF / STA / AP / AP+STA)
  2) AP 설정      (이름 / 비밀번호 / 채널 / IP)
  3) STA 설정     (SSID / 비밀번호 / IP)
  4) 주변 AP 스캔해서 고르기
  5) 호스트명
  6) 웹 UI (on/off, 포트)
  7) 지금 연결 / 끊기

  0) 뒤로
>
```

**무선 모드** — ESP32는 AP와 STA를 동시에 띄울 수 있다(`WIFI_AP_STA`).

| 모드 | 쓰임 |
|---|---|
| `OFF` | 무선 끔. 중계에 무선 부하를 전혀 주고 싶지 않을 때 |
| `STA` | 기존 공유기에 붙는다. 사내망에서 접속 |
| `AP` | 스스로 AP가 된다. 공유기가 없는 현장 |
| `AP+STA` (기본값) | 둘 다. 공유기에 붙으면서 AP도 유지 |

`AP+STA` 를 기본값으로 두는 이유는 **AP가 구조 통로**이기 때문이다.
STA 설정을 잘못 넣어 공유기에 못 붙어도, AP로는 항상 들어와 고칠 수 있다.

> **AP+STA의 제약.** ESP32는 무선이 하나뿐이라 AP와 STA가 **같은 채널을 써야 한다.**
> STA가 공유기(채널 N)에 붙는 순간 AP도 채널 N으로 따라 옮겨가고, 그때
> **AP에 붙어 있던 기기는 잠깐 끊겼다 다시 붙는다.** 메뉴의 AP 채널 설정은
> AP 단독 모드에서만 의미가 있다는 뜻이다. 이 동작을 화면에 명시한다.

**기본값**

| 항목 | 기본값 |
|---|---|
| 무선 모드 | `AP+STA` |
| AP 이름 (SSID) | **`NMX1108_SNIFFER`** |
| AP 비밀번호 | `nmx11088` (WPA2 최소 8자) — 18장 검토 항목 |
| AP IP | `192.168.4.1` |
| AP 채널 | 6 |
| 호스트명 | `nmx-bridge` |
| 웹 UI | on, 포트 80 |

> **AP 비밀번호를 왜 기본으로 거는가.** 이 장비는 방송용 믹서의 제어선 한가운데에 있다.
> AP를 열어두면 전파가 닿는 누구나 접속해 설정을 바꾸거나(v4에서는 프레임 주입까지)
> 할 수 있다. 다만 기본 비밀번호는 이 문서에 적혀 있으니 **현장 투입 전에 반드시 바꾼다.**
> AP 이름이 여러 대일 때 겹치는 문제도 있는데, 기본값을 지정받았으므로 그대로 두고
> 필요하면 메뉴에서 뒤에 식별자를 붙인다.

**기타**

- 연결은 **비동기**로 한다. `WiFi.begin()` 후 상태만 폴링하고, 연결될 때까지 기다리며
  루프를 막지 않는다.
- 비밀번호는 화면에 `****` 로만 보여준다.
- 스캔은 수백 ms 동안 무선을 점유하고 AP 접속도 끊길 수 있으므로, 실행 전에 확인받는다.
- SSID는 최대 32자, 비밀번호는 최대 63자다.

### 13.4 RAW 스트림 보기

```text
--- RAW 스트림 --- [space]정지 [d]방향 [c]지우기 [ESC]나가기 ---
 00:12:03.114  C>M   AB 09 00 00 01 4A    |......J|
 00:12:03.240  M>C   AA D2 55 01 02 2A    |...U..*|
 00:12:03.902  C>M   AB 0B 00 00 02 47    |.......|
```

- HEX와 ASCII를 나란히 보여준다.
- `d` 로 방향 필터: 양방향 / `C>M` 만 / `M>C` 만.
- `space` 로 화면을 멈춰도 **수집과 중계는 계속된다.** 화면만 정지한다.

```text
  resync / incomplete      1 / 0           0 / 0
  skipped bytes               0               0
  마지막 프레임          0.4초 전        0.9초 전
  프레임 평균 간격         612 ms         1004 ms
---------------------------------------------------------
  CMD 히스토그램                C>M      M>C
    0x09  PGM_CH                412        0
    0x0B  NEXT_CH               298        0
    0xD2  STATUS_PGM_PVW        300      300
    0xD3  STATUS_EFFECT         300      300
    0x7E  (unknown)               2        0
---------------------------------------------------------
  r) 초기화   0) 뒤로
```

**CMD 히스토그램**과 **프레임 평균 간격**은 새로 넣는 항목이다.
전자는 어떤 명령이 실제로 쓰이는지를 한눈에 보여주고([ToDo.md](ToDo.md) C-5),
후자는 컨트롤러의 폴링 주기를 자동으로 답해준다([ToDo.md](ToDo.md) C-2).

### 13.7 System / Factory reset

```text
--- System ----------------------------------------------
   펌웨어    v3.0            uptime   01:23:45
   설정      정상 (v1)       free heap 210 KB
   리셋 사유 Power-on
---------------------------------------------------------
  1) 설정 텍스트로 덤프
  2) 장치 정보 자세히
  3) 재부팅

  9) Factory reset  — 모든 설정을 공장 기본값으로
  0) 뒤로
>
```

`9` 를 고르면 되돌릴 수 없으므로 두 단계로 확인한다.

```text
!! Factory reset
   아래 항목이 모두 공장 기본값으로 돌아가고 장치가 재부팅됩니다.
     - UART 핀 / Baud / Format      -> GPIO16,17 / 26,27  9600 8N1
     - AP 이름 / 비밀번호            -> NMX1108_SNIFFER / nmx11088
     - STA SSID / 비밀번호           -> (지워짐)
     - 무선 모드 / 웹 UI / 호스트명   -> AP+STA / on / nmx-bridge
     - 로그 및 디버그 설정            -> 기본값

   진행하려면 RESET 을 그대로 입력하세요 (취소는 Enter)
>
```

- `y` 한 글자가 아니라 **`RESET` 전체를 입력**하게 한다. 메뉴를 빠르게 넘기다 실수로
  누르는 것을 막기 위해서다.
- 동작은 NVS 네임스페이스를 통째로 지우고(`Preferences.clear()`) 즉시 재부팅한다.
  부팅 시 `magic` 이 없으므로 기본값으로 초기화된다.
- **하드웨어 탈출구** — 설정이 손상돼 메뉴조차 못 쓰는 상황에 대비해,
  부팅 직후 3초 안에 BOOT 버튼(GPIO0)을 누르고 있으면 같은 동작을 하게 한다.
  UART0 콘솔은 항상 115200 고정이라 대개는 메뉴로 해결되지만, 마지막 수단으로 둔다.

## 14. 웹 UI

AP 또는 STA로 접속해 브라우저에서 같은 기능을 쓴다. UART0 메뉴와 **같은 데이터를 보고
같은 설정을 바꾼다.** 한쪽에서 바꾼 값은 다른 쪽에도 즉시 반영된다.

### 14.1 접속 방법

| 경로 | 주소 |
|---|---|
| AP 접속 | `NMX1108_SNIFFER` 에 연결 후 `http://192.168.4.1` |
| STA 접속 | 공유기가 준 IP, 또는 `http://nmx-bridge.local` (mDNS) |

AP 모드에서는 **캡티브 포털**을 띄운다. AP에 붙으면 브라우저가 자동으로 설정 페이지를
열어 주므로 IP를 외울 필요가 없다. (DNS 서버가 모든 질의를 `192.168.4.1` 로 돌린다)

### 14.2 화면 구성

```text
┌────────────────────────────────────────────────┐
│ NMX Bridge Sniffer          relay ON  ● 정상   │
├────────────────────────────────────────────────┤
│ [상태] [RAW] [Unresolved] [UART] [Network] [Sys]│
├────────────────────────────────────────────────┤
│                                                │
│   CTRL->MAIN   bytes 12340 / relayed 12340     │
│   MAIN->CTRL   bytes  8210 / relayed  8210     │
│   chk BAD 3    unknown 2    unresolved 7       │
│                                                │
│   CMD 히스토그램                                │
│   0x09 PGM_CH   ████████████████  412          │
│   0xD2 STATUS   ████████████      300          │
│                                                │
└────────────────────────────────────────────────┘
```

| 탭 | 내용 | UART0 메뉴 대응 |
|---|---|---|
| 상태 | 통계, CMD 히스토그램, 링크 상태 | 13.6 |
| RAW | 실시간 바이트 스트림 (1초 폴링) | 13.4 |
| Unresolved | 미해독 패킷 목록 + 상세 | 13.5 |
| UART | 핀 / Baud / Format 변경 | 13.2 |
| Network | 무선 모드 / AP / STA / 웹 UI | 13.3 |
| Sys | 장치 정보, 재부팅, **Factory reset** | 13.7 |

### 14.3 구현 방침

- **페이지는 자체 완결.** HTML·CSS·JS를 플래시에 넣어 서빙한다. AP 모드에는 인터넷이
  없으므로 CDN을 참조하면 화면이 깨진다. 외부 라이브러리를 쓰지 않고 순수 JS로 만든다.
- **실시간 갱신은 폴링.** `GET /api/status` 를 1초 주기로 부르고 JSON을 받는다.
  WebSocket은 v4로 미룬다. 폴링이 단순하고, 1초면 관찰 용도로 충분하다.
- **RAW 탭만 예외적으로 빠르게.** 200~300ms 주기로 링버퍼의 새 바이트만 받아 이어붙인다.
  창을 벗어난 데이터는 서버 쪽 링버퍼가 덮어쓰므로, 놓친 구간은 표시해 준다.
- **설정 변경은 `POST /api/config`.** 받는 즉시 검증하고 Flash에 쓴다(16장).
  UART0 메뉴와 같은 검증 코드를 공유한다.
- **v3에서는 읽기와 설정만.** 프레임 주입 API(`/api/send`)는 만들지 않는다.
  장비로 무언가를 쏘는 것은 v4에서 인증과 함께 넣는다.

### 14.4 중계와의 관계

웹 서버는 **중계에 절대 끼어들면 안 된다.** HTTP 요청 하나를 처리하는 데 수십 ms가
걸릴 수 있고, WiFi 스택 자체도 지연을 만든다.

그래서 v3에서 **중계를 전용 FreeRTOS 태스크로 분리**한다(17장).
웹 서버와 메뉴는 `loop()` 에 남고, 중계는 별도 태스크에서 돌기 때문에
페이지를 아무리 많이 열어도 중계가 밀리지 않는다.

| | v2 (현재) | v3 |
|---|---|---|
| 중계 | `loop()` 폴링 | **전용 태스크** (코어 1, 높은 우선순위) |
| 로그·메뉴 | `loop()` | `loop()` |
| 웹 서버 | 없음 | `loop()` 또는 비동기 |
| WiFi 스택 | 없음 | 코어 0 |

## 15. Unresolved 패킷의 정의

"해석하지 못했다"를 명확히 해 둬야 버퍼에 무엇이 쌓일지 결정된다. 아래 5종으로 잡는다.

| 사유 | 조건 | 왜 중요한가 |
|---|---|---|
| `BAD_CHK` | 체크섬 불일치 | 프레임 구조나 패리티 가정이 틀렸을 신호 |
| `UNKNOWN_CMD` | CMD가 NMX-1106 문서에 없음 | **NMX-1108 전용 명령 후보** |
| `OUT_OF_RANGE` | CMD는 알지만 데이터가 문서 범위 밖 (`EFFECT RAW 0x..?`, `SETUP KEY 0x..?` 등) | CH7/CH8 같은 확장값 후보 |
| `INCOMPLETE` | 6바이트가 차기 전에 50ms 이상 끊김 | 프레임 길이 가정이 틀렸을 신호 |
| `ORPHAN` | 헤더 없이 흘러다닌 바이트 (`SKIP`) | 동기 문제 또는 다른 프레임 구조 |

`PGM CH 7?` 처럼 **`?` 가 붙은 추정 디코딩은 unresolved로 넣지 않는다.**
해석 자체는 됐고 확증이 없을 뿐이라 양이 많아 버퍼를 밀어내기 때문이다.
대신 통계에 `추정 디코딩` 카운터를 따로 둔다.

**저장 위치** — 링버퍼는 RAM에 둔다. 기본 10개, 설정에서 최대 32개까지.
재부팅하면 사라지는데, Flash에 쓰면 수명이 닳고 잡음이 심할 때 쓰기가 폭주하기 때문이다.
필요하면 `e) 텍스트 덤프` 로 화면에 뽑아 복사해 둔다.

> 설정값은 변경 즉시 Flash에 쓰지만(16장), **패킷 데이터는 절대 쓰지 않는다.**
> 설정 변경은 사람이 하는 일이라 평생 수백 번이지만, 패킷은 초당 수십 개씩 들어온다.

## 16. 설정 영속화

ESP32 Arduino의 **Preferences**(NVS) 를 쓴다. 구조체를 통째로 `putBytes` 로 저장한다.
키를 하나씩 저장하지 않는 이유는 갱신이 원자적이고 버전 관리가 쉽기 때문이다.

```cpp
struct Config {
    uint32_t magic;        // 'NMX1' 손상/미초기화 판별
    uint16_t version;      // 구조 변경 시 마이그레이션
    uint16_t size;

    struct Uart {
        int8_t   rxPin, txPin;
        uint32_t baud;
        uint8_t  format;   // 0=8N1 1=8E1 2=8O1 3=7E1 4=7O1
    } uart[2];             // [0]=컨트롤러측 [1]=본체측

    uint8_t  wifiMode;     // 0=OFF 1=STA 2=AP
    char     ssid[33];
    char     pass[65];
    uint8_t  staUseDhcp;
    uint32_t staIp, staGw, staMask, staDns;

    char     apSsid[33];        // 기본값 "NMX1108_SNIFFER"
    char     apPass[65];        // 기본값 "nmx11088"
    uint8_t  apChannel;         // 기본값 6
    uint32_t apIp;              // 기본값 192.168.4.1

    char     hostname[33];      // 기본값 "nmx-bridge"
    uint8_t  webEnabled;        // 기본값 on
    uint16_t webPort;           // 기본값 80
    uint16_t tcpPort;           // v4 원격 제어용. 지금은 자리만

    uint8_t  frameLogEnabled;
    uint8_t  rawLogEnabled;
    uint8_t  unresolvedDepth;   // 기본 10, 최대 32
    uint8_t  ansiEnabled;

    Uart     uartBackup[2];     // UART 롤백용 직전 값
    uint8_t  uartPending;       // 확인 대기 중이면 1

    uint32_t crc32;        // 위 전체의 체크섬
};
```

### 16.1 저장 시점 — 변경 즉시

**"저장" 메뉴는 없다.** 값이 확정되는 순간 Flash에 기록한다.
UART0 메뉴에서 바꾸든 웹 UI에서 바꾸든 같다.

"확정되는 순간"의 기준은 이렇다.

| 입력 종류 | 저장 시점 |
|---|---|
| 숫자·항목 선택 (Baud, 모드, on/off …) | 고른 즉시 |
| 문자열 입력 (SSID, 비밀번호, 호스트명) | **Enter로 필드를 확정할 때.** 한 글자마다 쓰지 않는다 |
| UART 핀·Baud·Format | 즉시 저장 + 30초 확인 (13.2 참조) |

저장에 성공하면 화면에 `saved` 를 짧게 표시한다. 실패하면 이유를 남긴다.

### 16.2 플래시 수명

값 하나 바꿀 때마다 구조체 전체를 다시 쓰는 방식이라 낭비처럼 보이지만, 실제로는 문제가 없다.

- NVS는 **자체 wear leveling** 을 한다. 같은 물리 섹터를 반복해서 지우지 않는다.
- 플래시 섹터 내구성은 보통 10만 회 수준이다.
- 설정 변경은 **사람이 메뉴를 조작할 때만** 일어난다. 하루에 100번씩 바꿔도 수년치다.

반면 **패킷 데이터는 절대 Flash에 쓰지 않는다.** 초당 수십 개씩 들어오므로
같은 방식으로 저장하면 금세 수명을 태운다. Unresolved 링버퍼가 RAM에 있는 이유다(15장).

### 16.3 잘못된 값이 굳는 문제

즉시 저장의 위험은 **틀린 값도 즉시 굳는다**는 점이다. 세 겹으로 막는다.

1. **입력 검증.** 핀 번호, IP 형식, SSID 길이, 비밀번호 최소 8자 등을 저장 **전에** 거른다.
   통과하지 못한 값은 아예 쓰지 않는다.
2. **UART 설정 30초 롤백.** 새 값과 직전 값을 함께 저장하고, 확인이 없으면 되돌린 뒤
   그 결과도 저장한다. 어느 시점에 전원이 나가도 Flash에는 동작하던 설정이 남는다(13.2).
3. **AP는 항상 살아 있다.** STA 설정을 아무리 잘못 넣어도 AP로 들어와 고칠 수 있고,
   무선을 통째로 꺼도 **UART0 콘솔은 115200 고정**이라 항상 접근 가능하다.
   그래도 안 되면 Factory reset(13.7).

**손상 대응** — `magic` 이나 `crc32` 가 맞지 않으면 기본값으로 부팅하고 그 사실을 알린다.
`version` 이 낮으면 마이그레이션한다.

### 16.4 설정이 아닌 것 — 저장하지 않는 두 가지

`relay` 와 `inject` 는 **설정이 아니라 운전 상태**로 본다. Config 구조체에 넣지 않고,
부팅할 때마다 고정값으로 시작한다.

| 항목 | 부팅값 | 이유 |
|---|---|---|
| `relay` | 항상 **ON** | `off` 로 굳은 채 재부팅하면 믹서가 먹통이 되고, 원인을 찾기도 어렵다 |
| `inject` | 항상 **off** | 부팅하자마자 장비로 프레임이 나가는 사고 방지 |

> 이 두 개도 저장하길 원하면 18장 검토표 7번에서 바꾼다. 다만 `relay=off` 가 저장되면
> **다음 부팅에서 믹서가 조용히 죽는다**는 점을 감안해야 한다.

**비밀번호 보관** — NVS는 기본적으로 암호화되지 않는다. 플래시를 덤프하면 WiFi 비밀번호와
AP 비밀번호가 평문으로 보인다. 필요하면 NVS 암호화를 켜야 하는데, 그러면 플래시
백업/복원이 까다로워진다. 이 장비의 용도상 과하다고 보고
**암호화 없이 가되, 문서에 명시**하는 쪽을 택했다.

## 17. 중계 무결성 원칙

메뉴가 아무리 화려해도 **중계를 막으면 실패**다.

### 17.1 중계를 전용 태스크로 분리

v2는 `loop()` 안에서 UART 버퍼를 폴링한다. `loop()` 가 하는 일이 로그 출력뿐일 때는
이걸로 충분했지만, v3에서는 메뉴 렌더링·WiFi·웹 서버가 같은 `loop()` 에 들어온다.
HTTP 요청 하나가 수십 ms를 잡아먹으면 그만큼 중계가 밀린다.

그래서 **중계만 떼어 별도 FreeRTOS 태스크로 옮긴다.**

```text
코어 0                          코어 1
┌─────────────────┐            ┌──────────────────────────┐
│ WiFi / TCP 스택 │            │ relayTask  (우선순위 높음)│
│ (ESP-IDF)       │            │   uart_read_bytes() 대기  │
└─────────────────┘            │   → 반대편 write          │
                               ├──────────────────────────┤
                               │ loopTask   (우선순위 1)   │
                               │   메뉴 / 웹 / 로그 / 통계 │
                               └──────────────────────────┘
```

- `relayTask` 는 `uart_read_bytes()` 에서 **블로킹 대기**한다. 데이터가 없으면 CPU를
  전혀 쓰지 않고, 바이트가 오면 즉시 깨어나 반대편으로 넘긴다.
- 우선순위를 `loopTask` 보다 높게 두어, 웹 요청을 처리하는 중이라도 **선점**한다.
- 파싱·통계·로그는 중계 경로에서 빼내 큐로 넘긴다. 중계는 옮기는 일만 한다.

이렇게 하면 `loop()` 가 무엇을 하든 중계 지연이 사실상 사라진다.

### 17.2 나머지 원칙

1. **메뉴 출력은 논블로킹 큐로.** 화면 한 장을 `Serial.print` 로 한 번에 쏟지 않고,
   출력 대기열에 넣어 `availableForWrite()` 만큼씩 흘려보낸다.
2. **WiFi 작업은 비동기로.** 연결·스캔에서 블로킹 호출을 쓰지 않는다.
   스캔은 무선을 오래 점유하고 AP 접속도 끊으므로 사전 확인을 받는다.
3. **웹 페이지는 가볍게.** 자체 완결 단일 페이지, 폴링 주기 1초.
   응답 JSON은 작게 유지한다.
4. **UART 재설정은 짧게.** `end()` → `begin()` 사이에 통신이 끊기므로,
   그 순간 진행 중이던 프레임은 유실될 수 있음을 알리고 확인받는다.
5. **중계 통계로 검증.** `bytes == relayed` 가 유지되는지 메뉴 머리말과 웹 상단에
   상시 표시한다.
6. **메뉴 진입이 수집을 멈추지 않는다.** 화면 출력만 멈추고 파서·통계·링버퍼는 계속 돈다.

## 18. 검토가 필요한 결정사항

구현 전에 확인받고 싶은 항목이다.

| # | 결정 | 택한 안 | 대안 |
|---|---|---|---|
| 1 | 메뉴 조작 방식 | 숫자 키 + Enter | ANSI 화살표 키 (터미널 호환성 문제) |
| 2 | 기존 텍스트 명령 | 유지 (메뉴와 병행) | 메뉴로 일원화 |
| 3 | UART 설정 적용 | 즉시 적용·저장 + 30초 미확인 시 자동 롤백 | 재부팅 후 적용 |
| 4 | Unresolved 저장 | RAM 링버퍼 (재부팅 시 소실) | NVS 저장 (플래시 수명 소모) |
| 5 | Unresolved에 `?` 추정 포함 | 제외 (별도 카운터) | 포함 |
| 6 | WiFi·AP 비밀번호 보관 | NVS 평문 | NVS 암호화 |
| 7 | `relay`·`inject` 저장 | **저장 안 함.** 운전 상태로 보고 ON/off 고정 부팅 | 설정으로 보고 저장 |
| 8 | 메뉴 진입 키 | `ESC` 또는 빈 줄 Enter | 별도 명령어 (`menu`) |
| 9 | **AP 기본 비밀번호** | `nmx11088` 을 걸어두고 "현장 전 변경" 안내 | 개방 AP (편하지만 누구나 접속) |
| 10 | **기본 무선 모드** | `AP+STA` (AP를 구조 통로로 상시 유지) | `AP` 만 / `OFF` 로 시작 |
| 11 | **웹 실시간 갱신** | HTTP 폴링 1초 (RAW 탭만 200~300ms) | WebSocket (v4로 미룸) |
| 12 | **문자열 입력 저장 시점** | Enter로 필드 확정 시 | 한 글자마다 (플래시 낭비) |
| 13 | **Factory reset 확인** | `RESET` 전체 입력 + BOOT 버튼 탈출구 | `y/N` 한 글자 |
| 14 | **웹에서 프레임 주입** | v3에서는 제공 안 함 | v3에 포함 (인증 필요) |

## 19. 구현 단계 제안

한 번에 다 만들지 않고 나눠서, 각 단계마다 중계가 멀쩡한지 확인하며 진행한다.

| 단계 | 내용 | 검증 |
|---|---|---|
| 1 | **중계를 전용 태스크로 분리** (17.1) | 기존 기능 그대로, `bytes == relayed` 유지 |
| 2 | Config 구조체 + NVS **즉시 저장** + Factory reset | 값 바꾸고 바로 전원 차단 → 재부팅 시 유지. 손상 시 기본값 복구 |
| 3 | 메뉴 프레임워크 (모드 전환, 논블로킹 출력 큐) | 메뉴 조작 중 `bytes == relayed` 유지 |
| 4 | UART 설정 메뉴 + 핀 검증 + 30초 롤백 | 보레이트를 바꿔 통신이 깨지고 30초 후 복구되는지. 롤백 도중 전원 차단 시에도 동작하는 값이 남는지 |
| 5 | Debug 메뉴 (RAW / Unresolved / 통계) | ToDo A-5를 메뉴로 재현 |
| 6 | Network 메뉴 + 비동기 WiFi (AP / STA / AP+STA) | WiFi 켠 상태로 ToDo A-5 재실행. AP+STA에서 채널 이동 시 동작 확인 |
| 7 | 웹 UI (상태·RAW·Unresolved 읽기) | 여러 브라우저로 동시 접속하며 `bytes == relayed` 유지 |
| 8 | 웹 UI 설정 변경 + 캡티브 포털 | 웹에서 바꾼 값이 UART0 메뉴에도 즉시 보이는지 |

**1단계를 맨 앞에 둔 이유** — 나머지가 전부 `loop()` 를 무겁게 만드는 작업이다.
중계를 먼저 떼어놓지 않으면, 이후 단계에서 지연이 생겼을 때 원인이 무엇인지 가려내기 어렵다.

# 4부. 이후 계획

## 20. v4 — 네트워크 제어

v3에서 잡아두는 구조가 다음 단계로 이어지도록 한다.

- **설정 구조체에 `tcpPort` 자리를 미리 만든다.** v4에서 TCP/WebSocket 서버가 쓸 포트다.
- **프레임 주입 경로를 한 곳으로 모은다.** 지금의 `sendmain`/`sendctrl` 이 쓰는 함수를
  나중에 네트워크 핸들러가 그대로 호출하게 한다. 주입 경로가 하나면 안전장치도 한 곳에만 둔다.
- **통계·상태를 구조체로 노출한다.** 메뉴가 읽어 그리는 그 데이터를
  v4에서 JSON으로 직렬화해 웹 UI에 보낸다.
- **WiFi가 중계에 주는 영향을 v3에서 미리 측정한다.** WiFi를 켠 상태로
  [ToDo.md](ToDo.md) A-5(중계 무결성)를 다시 돌려 `bytes == relayed` 가 유지되는지 본다.
  여기서 문제가 나오면 v4에서 중계를 별도 FreeRTOS 태스크로 분리해야 한다.

## 21. 그 이후 아이디어

1. CSV 로그 출력
2. 버튼 이벤트별 자동 라벨링
3. Wi-Fi 웹 UI를 통한 영상믹서 제어
4. WebSocket 기반 실시간 상태 모니터링
5. SD 카드 로그 저장
6. ESP32가 컨트롤러를 완전히 대체하는 standalone controller 모드

## 부록 A. 설계 변경 이력

| 버전 | 변경 | 이유 |
|---|---|---|
| v1 | 수동 감청(passive tap). RX만 연결, TX는 UART에 할당조차 안 함 | 장비 통신에 영향을 주지 않는 것이 최우선이었다 |
| v2 | **브리지(중계) 방식으로 전환.** 원래 케이블을 끊고 ESP32가 통로가 된다 | 최종 목표가 네트워크 기반 제어 디바이스이므로, 주입 경로를 미리 갖춰 두는 편이 낫다고 판단 |
| v2 | 빌드 환경을 `esp32dev` 하나로 통합. `ENABLE_INJECTION` 매크로 폐지 | 브리지에서는 TX가 기본으로 연결되므로 컴파일 타임 분기가 무의미해졌다. 송신은 런타임 `inject on` 으로만 막는다 |
| v3 (설계) | UART0 메뉴 + 설정 영속화 + WiFi | 재빌드 없이 핀·보레이트를 바꾸고, 분석에 필요한 정보를 화면으로 정리해서 본다 |

v1의 수동 감청 방식은 **장비 통신을 절대 건드리면 안 되는 상황**에서는 여전히 더 안전하다.
브리지는 ESP32가 죽으면 믹서 조작이 멈추기 때문이다. 실사용 중인 장비에서 관찰만 하려면
v1 방식으로 되돌리는 것을 고려한다.
