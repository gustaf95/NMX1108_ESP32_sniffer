# NMX-1108 RS-232C 패시브 스니퍼

NTU **NMX-1108** 8채널 영상믹서의 본체와 전용 컨트롤러를 잇는 **케이블은 그대로 둔 채**,
ESP32를 그 선에 **커플링(패시브 탭)** 으로 병렬로 붙여 오가는 RS-232C 프로토콜을
엿듣고 해석·기록한다.

최종 목표는 프로토콜을 완전히 파악한 뒤, **PC 또는 네트워크를 통해 믹서를 제어하는
대체 컨트롤러**를 만드는 것이다. 지금 단계는 그 전제가 되는 프로토콜 관찰이며,
이 단계에서는 **장비 통신에 일절 개입하지 않는 것**을 최우선으로 둔다.

NMX-1108의 공식 프로토콜 자료는 없다. 6채널 모델인 **NMX-1106 프로토콜 문서**를 기준으로
해석하고, NMX-1108에서 확장된 부분(CH7/CH8 등)은 미확인이므로 로그에 `?` 를 붙여 구분한다.

> **패시브 탭의 전제**
> 컨트롤러-본체를 잇던 원래 케이블은 **연결된 상태 그대로** 둔다. ESP32는 그 선에
> 수신기만 병렬로 얹어 신호를 듣기만 한다.
> 따라서 **ESP32의 전원이 꺼지든 펌웨어가 죽든 믹서 조작은 영향을 받지 않는다.**
> 실사용 중인 장비에 붙여도 되는 이유가 이것이다.

## 2. 하드웨어

### 2.1 연결 개념

ESP32는 통로가 아니라 **구경꾼**이다. 원래 케이블의 두 신호선에 리시버를 하나씩
병렬로 물려 흘러가는 신호를 복사해 읽을 뿐, 어느 선도 구동하지 않는다.

```text
      ┌──────────────────────────────────────────────┐
      │            원래 케이블 (그대로 유지)          │
 [컨트롤러] ═══════════════════════════════════ [본체]
      │                    │                          │
      │  ① 컨트롤러→본체   │  ② 본체→컨트롤러          │
      │      신호선        │      신호선               │
      ▼                    ▼
   R1IN                 R2IN
  ┌─────────────── MAX3232 ───────────────┐
  │  R1OUT                          R2OUT │
  └────┬──────────────────────────────┬───┘
       │                              │
    GPIO16                         GPIO26
  (Serial1 RX)                   (Serial2 RX)
        └──────── ESP32 ─────────────┘
```

**핵심은 화살표가 한 방향뿐이라는 것이다.** ESP32에서 바깥으로 나가는 선은 없다.

### 2.2 실제로 연결하는 선 (총 2가닥 + GND)

| # | ESP32 핀 | 성격 | 연결 상대 |
|---|---|---|---|
| 1 | GPIO16 `Serial1 RX` | 입력 | MAX3232 `R1OUT` (TTL 출력) |
| 2 | GPIO26 `Serial2 RX` | 입력 | MAX3232 `R2OUT` (TTL 출력) |
| — | GND | — | MAX3232 GND + 원래 케이블의 GND(신호 접지) |

MAX3232 쪽:

| MAX3232 핀 | 연결 |
|---|---|
| `R1IN` | 원래 케이블의 **컨트롤러→본체** 신호선 |
| `R2IN` | 원래 케이블의 **본체→컨트롤러** 신호선 |
| `T1IN`, `T2IN` | **연결하지 않는다** (또는 GND) |
| `T1OUT`, `T2OUT` | **연결하지 않는다.** 절대 케이블에 붙이지 않는다 |
| `VCC` / `GND` | ESP32 3V3 / GND |

- MAX3232 칩 하나에 **리시버가 2개** 들어 있으므로 **2채널 모듈 하나면 충분**하다.
  흔한 4핀 브레이크아웃(1채널)뿐이라면 2개를 쓰고 각각 `R1IN`/`R1OUT` 만 사용한다.
- **ESP32의 TX 핀은 아예 할당하지 않는다.** `Serial1.begin()` / `Serial2.begin()` 의
  TX 인자에 `-1` 을 넘겨 UART 드라이버가 어떤 핀도 출력으로 잡지 않게 한다.
  핀을 놀려두는 것과 드라이버가 잡고 있지 않은 것은 다르다.
- **드라이버 출력(`T*OUT`)을 케이블에 물리는 순간 이 방식의 안전성은 사라진다.**
  ESP32와 장비가 같은 선을 동시에 구동해 신호가 깨지고 소자가 상할 수 있다.
  송신이 필요하면 이 브랜치가 아니라 브리지 방식(`main` 브랜치)으로 간다.

핀 번호는 [../platformio.ini](../platformio.ini) 의 `build_flags` 에서
`-DTAP1_RX_PIN=...` 로 덮어쓰거나, v3에서는 메뉴로 바꾼다.
현재 설정은 `pins` 명령으로 확인한다.

### 2.3 어디를 탭할 것인가

가장 다루기 쉬운 지점은 **RJ45 케이블 양 끝 중 아무 곳이나 한쪽 포트**다.
한 포트에서 두 방향 신호가 모두 지나가므로, **한 군데만 물리면 양방향이 다 잡힌다.**

NMX-1106 자료 기준 RS-232C 포트 핀은 다음과 같다.

| RJ45 핀 | RS-232C 신호 |
|---:|---|
| 4번 | GND |
| 5번 | RxD |
| 6번 | TxD |

**이 표기는 장비 포트 기준일 가능성이 높다.** 컨트롤러 포트에서 탭한다면
`TxD`(6번)가 컨트롤러→본체, `RxD`(5번)가 본체→컨트롤러다. 본체 포트에서 탭하면 반대다.

만드는 방법은 두 가지다.

| 방법 | 설명 |
|---|---|
| **패스스루 어댑터** (권장) | RJ45 암-수 중계 어댑터를 열어 4·5·6번 핀에 탭선을 납땜한다. 원래 케이블을 훼손하지 않고, 빼면 원상복구된다 |
| 케이블 직접 탭 | 케이블 피복을 벗겨 해당 심선에 물린다. 되돌리기 어렵고 접촉 불량 위험이 있어 임시로만 |

> **방향을 틀려도 장비는 멀쩡하다.** 브리지 방식에서는 방향을 틀리면 믹서가 아예
> 동작하지 않아 오히려 판별이 쉬웠지만, 탭에서는 아무 일도 일어나지 않는다.
> 대신 **프레임 헤더 바이트로 소프트웨어가 방향을 판정**한다(4.2). 배선 단계에서
> 방향을 확신할 필요가 없다는 뜻이다.

### 2.4 전기적 주의사항

원래 수신기가 물려 있는 선에 수신기를 하나 더 병렬로 붙이는 것이므로,
**선을 끊는 것보다는 안전하지만 완전히 무부하는 아니다.**

1. **입력 임피던스.** EIA-232 규격상 드라이버는 3kΩ 부하를 구동할 수 있어야 하고,
   리시버 입력은 3k~7kΩ다. 병렬로 하나 더 붙이면 부하는 대략 절반(2.5kΩ 안팎)이 된다.
   9600bps·짧은 케이블에서는 대개 문제없지만, **규격 여유를 깎아먹는 것은 사실**이다.
2. **탭선은 짧게.** EIA-232는 부하 정전용량 2500pF까지를 가정한다. 탭선이 길면
   그만큼 정전용량이 늘어 파형이 둔해진다. **30cm 이내를 목표로 하고 1m를 넘기지 않는다.**
3. **RS-232C는 ±전압을 쓰므로 ESP32 GPIO에 직접 연결하지 않는다.** MAX3232를 반드시 거친다.
4. **GND는 반드시 공통으로 묶는다.** 신호 GND(RJ45 4번)를 MAX3232·ESP32와 공통으로 연결하지
   않으면 기준점이 없어 아무 데이터도 못 읽거나 엉뚱한 값이 읽힌다.
5. **ESP32를 USB로 PC에 물릴 때 접지 루프에 주의한다.** 장비와 PC의 접지 전위가 다르면
   GND선으로 전류가 흐른다. 증상이 의심되면 USB 절연 어댑터나 독립 전원(배터리/어댑터)을 쓴다.
6. **투입 순서.** 전원을 넣기 전에 `T*OUT` 이 케이블에 닿아 있지 않은지 육안으로 다시 확인한다.
   이 한 가지만 지키면 나머지는 되돌릴 수 있다.

### 2.5 브리지 방식과의 비교

| | 패시브 탭 (이 브랜치) | 브리지 (`main` 브랜치) |
|---|---|---|
| 원래 케이블 | **유지** | 제거, ESP32가 대체 |
| ESP32 연결선 | RX 2가닥 + GND | RX 2 + TX 2 + GND |
| MAX3232 | 리시버 2채널 (모듈 1개면 충분) | 모듈 2개 |
| ESP32 전원 차단 시 | **믹서 정상 동작** | **믹서 조작 멈춤** |
| 펌웨어 버그/리셋 영향 | 없음 | 통신 중단 가능 |
| 장비 전기적 부하 | 리시버 1개분 추가 | 없음(선이 끊겨 있음) |
| 프레임 주입 | **불가능** | 가능 (`inject on`) |
| 실사용 장비 투입 | 가능 | 권장하지 않음 |

이 브랜치의 목적은 **관찰 단계에서 장비를 절대 멈추지 않는 것**이다.
프레임 주입이 필요한 실험([ToDo.md](ToDo.md) F절)은 브리지 브랜치에서 한다.

## 3. 수집 설계

장비 통신에 개입할 수 없는 대신, **한 바이트도 놓치지 않는 것**이 최우선 목표가 된다.
탭에서는 흘려보낸 바이트를 되돌려 받을 방법이 없기 때문이다.

1. **두 포트를 완전히 독립적으로 파싱한다.** 각 방향은 별개의 스트림이며,
   한쪽 파서가 동기를 잃어도 다른 쪽에 영향을 주지 않는다.
2. **수집이 로그보다 우선.** UART RX 버퍼에서 바이트를 꺼내는 일을 먼저 하고,
   해석과 출력은 그 뒤에 한다.
3. **로그가 수집을 막지 않는다.** USB 출력 버퍼에 여유가 없으면 로그 줄을 통째로 버리고
   카운트만 올린다. 버려진 줄 수는 `stats` 의 `dropped log lines` 에 나온다.
4. **RX 버퍼를 넉넉히 잡는다.** 9600bps에서 초당 960바이트뿐이지만,
   긴 출력이 나가는 동안 밀릴 수 있으므로 포트당 512바이트 이상을 확보한다.
5. **오버플로를 조용히 넘기지 않는다.** RX 버퍼가 포화에 근접하면 `OVERFLOW` 로
   로그에 남기고 카운터를 올린다. **놓친 사실을 아는 것이 놓치지 않는 것 다음으로 중요하다.**

브리지 방식의 `bytes == relayed` 같은 자기 검증 지표가 여기엔 없다.
대신 `stats` 의 `overflow` 가 0인지, 프레임 평균 간격이 갑자기 벌어지지 않는지로 확인한다.

> **오버플로 검출의 한계.** 드라이버 링버퍼가 가득 차면 그 뒤에 도착한 바이트는
> 조용히 버려지고, **몇 바이트를 잃었는지 알 방법이 없다.** 그래서 정확한 유실 바이트 수가
> 아니라 **포화에 근접한 순간**(버퍼의 512바이트 중 480바이트 이상이 밀려 있는 상태)을
> 잡아 이벤트로 센다. 즉 `overflow > 0` 은 "이만큼 잃었다"가 아니라
> **"이 구간에서 잃었을 수 있다"** 는 뜻이다. 하드웨어 프레이밍 에러 API는 코어 버전에 따라
> 신뢰도가 달라 쓰지 않는다(5.2와 같은 이유).
> 값이 0이면 유실이 없었다고 봐도 되지만, 0이 아니면 그 구간의 통계는 신뢰하지 않는다.

## 4. 출력 형식

### 4.1 로그 한 줄의 구조

```text
[C>M] 00:00:12.345  AB 09 00 00 01 4A  CHK=OK   PGM CH 1
[C>M] 00:00:12.902  AB 0B 00 00 02 47  CHK=OK   NEXT CH 2
[M>C] 00:00:13.010  AA D2 55 01 02 2A  CHK=OK   STATUS PGM=CH1 PVW=CH2
[M>C] 00:00:13.300  AA D3 55 02 04 7C  CHK=BAD  STATUS EFFECT=1 INV=OFF ...  [expected CHK=26]
```

```text
[C>M] 00:00:12.345  AB 09 00 00 01 4A  CHK=OK   PGM CH 1
  │    │             │                  │        └ 디코딩 결과
  │    │             │                  └ 체크섬 판정
  │    │             └ 프레임 6바이트 HEX
  │    └ 타임스탬프. millis() 기반 HH:MM:SS.mmm
  └ 방향 태그 (고정 폭 5칸)
```

방향 태그를 **줄 맨 앞 고정 폭**에 두는 이유는, 터미널에서 눈으로 훑을 때 방향이
세로로 정렬되어 읽히고 `grep "\[C>M\]"` 로 한 방향만 걸러내기 쉽기 때문이다.

### 4.2 방향 태그

| 태그 | 뜻 |
|---|---|
| `[C>M]` | 컨트롤러 → 본체 |
| `[M>C]` | 본체 → 컨트롤러 |
| `[P1?]` / `[P2?]` | **방향 미확정.** 어느 포트에서 들어왔는지만 표시 |

브리지에서는 배선이 곧 방향이었지만, 탭에서는 두 신호선 중 어느 쪽이 컨트롤러 송신인지
배선만으로는 알 수 없다. 그래서 **프로토콜 자체로 판정**한다.

> 요청 프레임은 `0xAB`, 응답 프레임은 `0xAA` 로 시작한다(7장).
> **`0xAB` 가 우세한 포트가 컨트롤러측**이다.

`dir auto` (기본값) 동작:

1. 부팅 직후에는 방향 미확정 상태이며 `[P1?]` / `[P2?]` 로 찍는다.
2. 각 포트에서 **체크섬 OK인 프레임**의 첫 바이트를 센다. 체크섬이 맞아야만 세는 이유는,
   보레이트가 틀린 상태에서 나온 쓰레기 바이트에 낚이지 않기 위해서다.
3. 한 포트에서 20프레임 이상 모이고 그중 80% 이상이 한쪽 헤더로 쏠리면 확정한다.
4. 확정 시 `-- direction resolved: P1=CTRL, P2=MAIN --` 를 한 줄 남기고,
   이후 로그는 `[C>M]` / `[M>C]` 로 바뀐다.

수동으로 고정하고 싶으면 `dir p1=ctrl` / `dir p1=main` 을 쓰고, 이미 확정된 것을
뒤집으려면 `dir swap` 을 쓴다. **배선을 다시 만지지 않고 라벨만 바꾼다.**

### 4.3 프레임 외의 출력

프레임이 아닌 상황도 버리지 않고 남긴다.

| 표시 | 의미 |
|---|---|
| `RAW  ...` | `raw on` 모드의 원시 바이트 |
| `SKIP n byte(s): ...` | 헤더(`AB`/`AA`) 이전에 들어온 바이트 |
| `INCOMPLETE (n/6 bytes, timeout)` | 6바이트가 채워지기 전에 50ms 이상 끊긴 프레임 |
| `RESYNC from offset n` | 체크섬 불일치 후 프레임 내부 헤더에서 동기 재획득 |
| `OVERFLOW: rx buffer 486/512 ...` | **RX 버퍼 포화. 바이트를 놓쳤을 수 있다.** 탭에서는 복구 불가 |

체크섬이 틀려도 프레임은 반드시 출력하며, 알 수 없는 CMD도 `UNKNOWN CMD 0xNN` 으로 남긴다.
탭 방식에서는 **이 모든 판정이 순수한 관찰이며 장비에 어떤 영향도 주지 않는다.**

### 4.4 파서 동작

- `0xAB` 또는 `0xAA` 가 들어오면 프레임 수집을 시작하고, 6바이트가 차면 처리한다.
- **체크섬이 틀렸을 때만** 프레임 내부의 헤더 바이트에서 동기를 다시 잡는다.
  데이터에 `0xAB` 가 실릴 수 있어(페이더 값 등) 무조건 재동기하면 정상 프레임이 깨지기 때문이다.
- 프레임 길이는 6바이트 고정으로 가정한다 (검증은 [ToDo.md](ToDo.md) A-4).
- 파서 상태는 포트마다 따로 갖는다.

## 5. 보레이트 / 프레임 형식 변경

문서에 명시되지 않은 파라미터가 있고(패리티), 보레이트조차 실측 전이므로
**재빌드 없이 바꿀 수 있어야 한다.** 탭 방식에서는 값을 아무리 틀리게 넣어도
장비에 영향이 없으므로 마음껏 시도할 수 있다.

### 5.1 수동 변경

| 명령 | 기능 |
|---|---|
| `baud <n>` | **양쪽 포트** 보레이트 변경 |
| `baud1 <n>` / `baud2 <n>` | 포트별 개별 변경 |
| `format <fmt>` | 양쪽 프레임 형식 변경 |
| `format1 <fmt>` / `format2 <fmt>` | 포트별 개별 변경 |

지원 보레이트 `1200` / `2400` / `4800` / **`9600`** / `19200` / `38400` / `57600` / `115200`
지원 형식 **`8N1`** / `8E1` / `8O1` / `7E1` / `7O1` / `8N2`

```text
> baud 19200
UART1 9600 -> 19200 8N1
UART2 9600 -> 19200 8N1
(파서 상태 및 통계 초기화)
```

- 변경 시 `end()` → `begin()` 을 거치므로 **그 순간 진행 중이던 프레임은 유실**된다.
  탭에서는 되돌려 받을 수 없으므로, 유실 사실을 로그에 남긴다.
- 파서 상태와 방향 판정 통계는 함께 초기화한다. 이전 설정에서 모인 통계는
  새 설정에서 의미가 없기 때문이다.
- 포트를 따로 설정할 수 있게 한 이유는 **한쪽만 바꿔 비교**하기 위해서다.
  한 포트를 9600에 두고 다른 포트를 19200으로 돌려 어느 쪽에서 정상 프레임이
  나오는지 보면 판정이 빠르다.

### 5.2 자동 탐색 — `scan`

보레이트를 모르는 상태에서 하나씩 손으로 돌려보는 것은 느리다.
`scan` 은 후보 보레이트를 차례로 적용해 일정 시간 듣고 점수를 매긴다.

**점수는 체크섬이 맞는 6바이트 프레임의 개수로만 낸다.** 하드웨어 프레이밍 에러
플래그는 코어 버전에 따라 신뢰도가 달라서 쓰지 않는다. 우리는 프로토콜의 체크섬 식을
이미 알고 있으므로(7장), 이것이 훨씬 강한 신호다.

**두 포트를 동시에 훑는다.** 한 방향이 조용해도(C-1처럼 본체가 응답하지 않는 경우)
다른 방향에서 점수가 나오기 때문이다. 점수는 양쪽 `chk-ok` 의 합이다.

```text
> scan
scan: 8 baud x 1 format, 3초씩 (약 24초)
장비가 조용하면 아무것도 못 찾는다. 스캔 중 컨트롤러를 계속 조작한다.
아무 키나 누르면 중단한다.
   baud   fmt    p1 f/ok    p2 f/ok   score
   1200   8N1        0/0        0/0       0
   2400   8N1        0/0        0/0       0
   4800   8N1       12/0        8/0       0
   9600   8N1      41/41      30/30      71  <-- best
  19200   8N1        6/0        2/0       0
  38400   8N1        0/0        0/0       0
  57600   8N1        0/0        0/0       0
 115200   8N1        0/0        0/0       0
result: 9600 8N1  score=71  (confidence high)
apply? (y/N)
```

- 후보당 기본 3초, `scan <초>` 로 1~30초 사이에서 조정한다. **장비가 조용하면 아무것도
  못 찾으므로, 스캔 중에는 컨트롤러 버튼을 계속 눌러 트래픽을 만든다.**
- `f/ok` 는 `잡힌 프레임 수 / 체크섬 OK 수`다. `ok` 가 0인데 `f` 만 잡히는 줄은
  우연히 헤더 값이 나온 것이므로 무시한다.
- `confidence` 는 최고 점수와 2위 점수의 차이로 매긴다.
  `high` = 10점 이상이면서 2위의 3배 이상, `medium` = 5점 이상, 나머지는 `low`.
- 스캔 중 아무 키나 누르면 중단하고 **원래 설정으로 되돌린다.** 채택 여부와 무관하게
  스캔이 끝나면 항상 원래 설정으로 복귀한 뒤 `apply?` 를 묻는다.
- 최고 점수가 0이면 실패로 보고한다. 프레임 형식(`8E1` 등)을 바꿔 다시 돌리거나,
  `scan full` 로 형식까지 훑거나, `raw on` 으로 원시 바이트를 본다.
- 형식까지 훑는 `scan full` 은 보레이트 8종 × 형식 6종 = 48회이므로 3초씩이면 약 2분 걸린다.
  기본 `scan` 은 현재 형식으로 보레이트만 훑는다.

# 2부. 프로토콜

> 이 부의 내용은 연결 방식과 무관하다. 브리지든 탭이든 프로토콜 해석은 동일하다.

## 8. 프레임 구조

6바이트 고정 길이. 요청/제어는 `AB`, 응답은 `AA` 로 시작한다.

```text
요청  AB CMD D1 D2 D3 CHK
응답  AA CMD D1 D2 D3 CHK

CHK = (0x54 - CMD - D1 - D2 - D3) & 0xFF
```

체크섬 식은 **원문 문서의 예제 프레임 78개 전부와 일치**하는 것을 확인했다.
이 식이 방향 자동 판정(4.2)과 보레이트 자동 탐색(5.2)의 근거가 된다.

```cpp
uint8_t nmxChecksum(const uint8_t frame[6]) {
    return static_cast<uint8_t>(0x54 - frame[1] - frame[2] - frame[3] - frame[4]);
}
```

## 9. 명령표

CMD 요약이다. 상세 값은 9.1 이하에 있다.

| CMD | 의미 |
|---:|---|
| `0x01` | SETUP key |
| `0x02` | Audio Select EXT |
| `0x05` | Effect Number / Effect INV |
| `0x06` | Fader Mode CUT/TAKE |
| `0x07` | Manual Fader value (`D2:D3` 16비트) |
| `0x08` | PGM overlay CKEY/DSK/PIP 비트마스크 |
| `0x09` | PGM CH |
| `0x0B` | NEXT/PVW CH |
| `0xD0` | Default |
| `0xD2` | PGM/PVW 상태 요청·응답 |
| `0xD3` | EFFECT/CKEY/PIP/DSK/AUDIO 상태 요청·응답 |

### 9.1 SETUP (`0x01`)

```text
AB 01 00 00 06 4D   SETUP ENTER (MENU)
AB 01 00 00 08 4B   SETUP ESC
AB 01 00 00 01 52   SETUP UP?      ← 원문 한글 깨짐. 추정
AB 01 00 00 00 53   SETUP DOWN?    ← 원문 한글 깨짐. 추정
AB 01 00 00 03 50   SETUP LEFT     (sub menu -)
AB 01 00 00 02 51   SETUP RIGHT    (sub menu +)
```

### 9.2 Audio Select EXT (`0x02`)

```text
AB 02 00 00 00 52   EXT OFF
AB 02 00 00 01 51   EXT ON
```

### 9.3 EFFECT (`0x05`)

`D3` 의 하위 니블이 번호, `0x10` 비트가 INV 플래그다.

```text
AB 05 00 00 01 4E   EFFECT 1 (좌우)      AB 05 00 00 11 3E   EFFECT 1 INV
AB 05 00 00 02 4D   EFFECT 2 (상하)      AB 05 00 00 12 3D   EFFECT 2 INV
AB 05 00 00 03 4C   EFFECT 3             AB 05 00 00 13 3C   EFFECT 3 INV
AB 05 00 00 04 4B   EFFECT 4             AB 05 00 00 14 3B   EFFECT 4 INV
AB 05 00 00 05 4A   EFFECT 5             AB 05 00 00 15 3A   EFFECT 5 INV
AB 05 00 00 06 49   EFFECT 6             AB 05 00 00 16 39   EFFECT 6 INV
AB 05 00 00 07 48   EFFECT 7 (FOUT/IN)   AB 05 00 00 17 38   EFFECT 7 INV
AB 05 00 00 08 47   EFFECT 8 (MIX)       AB 05 00 00 18 37   EFFECT 8 INV
```

### 9.4 FADER MODE (`0x06`) / FADER 값 (`0x07`)

```text
AB 06 00 00 01 4D   FADER MODE TAKE
AB 06 00 00 02 4C   FADER MODE CUT

AB 07 00 00 00 4D   FADER OFF
AB 07 00 00 11 3C   값 0x011
AB 07 00 00 FF 4E   값 0x0FF
AB 07 00 01 00 4C   값 0x100
AB 07 00 01 FF 4D   값 0x1FF
```

`0x07` 은 `D2:D3` 를 16비트로 합친 값이 페이더 위치다. 원문 예제 범위는 `0x000`~`0x1FF`.

### 9.5 PGM 오버레이 (`0x08`)

`D3` 가 비트마스크다. bit0=CKEY, bit1=DSK, bit2=PIP.

```text
AB 08 00 00 00 4C   ALL OFF
AB 08 00 00 01 4B   CKEY
AB 08 00 00 02 4A   DSK
AB 08 00 00 04 48   PIP
AB 08 00 00 03 49   DSK + CKEY
AB 08 00 00 05 47   PIP + CKEY
AB 08 00 00 06 46   PIP + DSK
AB 08 00 00 07 45   ALL ON
```

### 9.6 PGM CH (`0x09`) / NEXT·PVW CH (`0x0B`)

`D3` 에 채널 번호가 그대로 실린다.

```text
AB 09 00 00 00 4B   PGM CH OFF      AB 0B 00 00 00 49   NEXT CH OFF
AB 09 00 00 01 4A   PGM CH1         AB 0B 00 00 01 48   NEXT CH1
AB 09 00 00 02 49   PGM CH2         AB 0B 00 00 02 47   NEXT CH2
AB 09 00 00 03 48   PGM CH3         AB 0B 00 00 03 46   NEXT CH3
AB 09 00 00 04 47   PGM CH4         AB 0B 00 00 04 45   NEXT CH4
AB 09 00 00 05 46   PGM CH5         AB 0B 00 00 05 44   NEXT CH5
AB 09 00 00 06 45   PGM CH6         AB 0B 00 00 06 43   NEXT CH6
```

NMX-1108 확장 **추정값** (실측 필요, [ToDo.md](ToDo.md) B-1·B-2):

```text
AB 09 00 00 07 44   PGM CH7?        AB 0B 00 00 07 42   NEXT CH7?
AB 09 00 00 08 43   PGM CH8?        AB 0B 00 00 08 41   NEXT CH8?
```

### 9.7 Default (`0xD0`)

```text
AB D0 00 00 01 83   Default
```

### 9.8 상태 조회 (`0xD2`, `0xD3`)

```text
AB D2 00 00 01 81   요청: PGM CH, PVW CH
AA D2 55 01 02 2A   응답 예: PGM=CH1, PVW=CH2

AB D3 00 00 01 80   요청: EFFECT, CKEY/PIP/DSK/AUDIO
AA D3 55 xx xx --   응답
```

응답의 3번째 바이트는 `0x55` 고정으로 보인다.

**`D2` 응답 — 채널 비트마스크** (4번째=PGM, 5번째=PVW)

| 값 | 의미 |
|---:|---|
| `0x01` | CH1 |
| `0x02` | CH2 |
| `0x04` | CH3 |
| `0x08` | CH4 |
| `0x10` | CH5 |
| `0x20` | CH6 |
| `0x40` | **OFF** (NMX-1106 기준) |

NMX-1108에서 CH7/CH8이 들어갈 자리인 `0x40` 을 이미 OFF가 쓰고 있다.
**OFF 코드가 바뀌었거나 CH7/CH8이 다른 방식으로 실린다는 뜻**이므로 실측이 필요하다
([ToDo.md](ToDo.md) B-3).

**`D3` 응답 — 상태 비트**

4번째 바이트:

| 비트 | 의미 |
|---|---|
| bit0 | EFFECT INV |
| bit1~bit7 | EFFECT 1 ~ EFFECT 7 |

5번째 바이트:

| 비트 | 의미 |
|---|---|
| bit0 | EFFECT 8 |
| bit1 | CG |
| bit2 | PIP |
| bit3 | DSK |
| bit4, bit5 | Fixed 0 |
| bit6 | EXT AUDIO |
| bit7 | Fixed 0 |

## 10. NMX-1108에서 확인해야 할 것

NMX-1108 확장분은 아직 추정이라, 펌웨어가 해당 구간을 로그에 `?` 로 표시한다.

| 로그 표시 | 뜻 |
|---|---|
| `PGM CH 7?` / `NEXT CH 8?` | 채널 명령이 NMX-1106 규칙의 연장인지 미확인 |
| `PGM=OFF\|CH7?` | `D2` 응답의 `0x40` 이 OFF인지 CH7 비트인지 미확인 |
| `CH8?` | `0x80` 을 CH8로 가정 |
| `fixed-0 bits set: 0x..?` | 문서상 0이어야 할 비트가 켜짐. 8채널 확장 신호일 수 있음 |
| `UNKNOWN CMD 0xNN` | NMX-1106 문서에 없는 명령 |

항목별 테스트 절차와 판정 기준은 **[ToDo.md](ToDo.md)** 에 정리해 두었다.
플래시 직후 `selftest` → 탭 배선·방향 확인 → 보레이트/형식 확정(`scan`) 순으로 진행한다.

프로토콜이 예상과 완전히 다르면 `raw on` 으로 전환해 원시 바이트부터 관찰한다.

### 10.1 탭 방식에서의 ToDo 조정

[ToDo.md](ToDo.md) 는 이 브랜치 기준으로 갱신해 두었다. 항목 번호는 그대로 두고
브리지를 전제하던 절차만 바꿨다.

| ToDo 항목 | 바뀐 내용 |
|---|---|
| A-2 | 배선 방향 및 **중계 성립** → **탭 배선 및 방향 판정.** 믹서가 동작하는지로 판별하던 근거가 사라져, 바이트 유입과 `dir` 확정으로 본다 |
| A-3 | 통신 파라미터 8N1 → **통신 파라미터 확정.** `scan` 으로 재빌드 없이 훑는다 |
| A-5 | **중계** 무결성 → **수집 무결성.** `bytes == relayed` 대신 `overflow == 0` 으로 본다(3장) |
| A-6 | 전원 차단 시 동작 → **탭 무해성 확인.** 장비에 영향이 없다는 것을 한 번 실증한다 |
| C-6 | `relay off` 실험과 주입 실험을 삭제하고 관찰 1~3으로 교체. **모델 A는 관찰만으로 확정되지만 모델 B는 정황까지만 나온다** |
| D-3 송신 실험 | **삭제.** 절차를 걷어내고 ToDo F절에 목록만 남겼다 |

나머지 항목(B 전체, C-1~C-5, D-1·D-2)은 전부 관찰만으로 가능하므로 그대로 유효하다.
**오히려 실사용 중인 장비에 붙일 수 있어 실제 운용 트래픽을 볼 수 있다는 이점이 생긴다.**

막히는 지점은 하나다. **C-1에서 컨트롤러가 `D2` 요청을 아예 보내지 않으면**
본체 응답을 볼 수 없고, 가장 불확실한 B-3도 함께 막힌다. 그때는 B-3만 브리지 브랜치로 넘긴다.

# 3부. [설계안] v3 — UART0 메뉴 + WiFi

> **미구현. 검토용이다.** 아래 내용은 아직 코드에 반영하지 않았다.
> 확정되면 그때 구현한다.

## 11. 배경과 범위

지금은 `raw on` 같은 텍스트 명령을 외워서 쳐야 하고, 핀을 바꾸려면 재빌드해야 하며,
설정은 재부팅하면 사라진다. 또 프로토콜 분석에 정작 필요한 정보 — 어떤 CMD가 몇 번 왔는지,
해석 못 한 패킷이 무엇이었는지 — 는 흘러가는 로그를 눈으로 훑어야 찾을 수 있다.

| 포함 | 제외 (v4 이후) |
|---|---|
| UART0 메뉴 UI | 네트워크로 **프레임 주입** |
| 설정 **변경 즉시** Flash 저장 | WebSocket 실시간 스트림 |
| 탭 포트 핀·보레이트·프레임형식 런타임 변경 | OTA 업데이트 |
| WiFi **AP / STA / AP+STA 동시** | SD 카드 로깅 |
| **웹 UI** — 메뉴와 같은 기능을 브라우저로 | 스탠드얼론 컨트롤러 모드 |
| RAW 뷰 / Unresolved 버퍼 / 패킷 통계 | |
| Factory reset | |

WiFi와 웹 UI를 v3에 넣는 이유는, 최종 목표인 **네트워크 제어 디바이스**로 가기 전에
무선과 HTTP 처리가 수집에 지장을 주지 않는지 먼저 확인해 두기 위해서다.
웹에서 **읽고 설정하는 것까지가 v3**이고, 장비로 **프레임을 쏘는 것은 브리지 방식으로
넘어간 뒤의 이야기**다.

> **탭 방식이라 v3가 덜 위험해진다.** 브리지에서는 웹 서버 지연이 곧 믹서 조작 지연이라
> 중계를 전용 태스크로 빼는 것이 필수였다. 탭에서 최악의 결과는 **로그 일부 유실**이다.
> 그래도 유실은 되돌릴 수 없으므로 수집 태스크 분리는 그대로 한다(18장).

## 12. 동작 모드

UART0 하나로 로그와 메뉴를 같이 쓸 수 없으므로 모드를 나눈다.

| 모드 | 화면 | 진입 |
|---|---|---|
| **모니터 모드** (기본) | 프레임/RAW 로그가 계속 흐른다. 기존 텍스트 명령도 그대로 동작 | `ESC` 또는 `0` + Enter |
| **메뉴 모드** | 로그 출력 중단, 메뉴 UI 표시 | `ESC` 또는 빈 줄에서 Enter |

**두 모드 모두에서 수집은 멈추지 않는다.** 메뉴를 보는 동안 지나간 패킷도
Unresolved 버퍼와 통계에는 그대로 반영된다. 화면에 안 뿌릴 뿐이다.

기존 텍스트 명령(`stats`, `raw on` …)은 없애지 않는다. 메뉴보다 빠르고 로그로 남기기 좋다.

## 13. 메뉴 트리

```text
메인
├─ 1) Network 설정

│    ├─ 1-2) AP 설정
│    │        ├─ AP 이름(SSID)     기본값 NMX1108_SNIFFER
│    │        ├─ AP 비밀번호
│    │        ├─ AP 채널

│    ├─ 1-3) STA 설정
│    │        ├─ SSID 직접 입력 / 주변 AP 스캔해서 고르기

│    ├─ 1-4) 호스트명             기본값 nmx-sniffer
│    ├─ 1-5) 웹 UI (on / off, 포트)
│    └─ 1-6) 지금 연결 / 끊기 · 현재 상태
├─ 2) 탭 포트 설정
│    ├─ 포트1 RX 핀 / Baud / Format
│    ├─ 포트2 RX 핀 / Baud / Format
│    ├─ 양쪽 동일하게 적용

├─ 3) Debug / Monitor
│    ├─ 3-1) RAW 스트림 보기
│    ├─ 3-2) Unresolved 패킷 (최근 10개)
│    ├─ 3-3) 패킷 상태 / 통계

│    ├─ 4-1) 설정 텍스트로 덤프
│    ├─ 4-2) 장치 정보 (버전 / uptime / free heap / 리셋 사유)
│    ├─ 4-3) 재부팅
│    └─ 4-4) Factory reset  ← 모든 설정을 공장 기본값으로
└─ 0) 모니터 모드로 복귀

조작은 **숫자 키 + Enter** 방식으로 한다. 화살표 키(ANSI 이스케이프)는
`pio device monitor` 나 다른 터미널에서 동작이 제각각이고 `ESC` 키와 충돌하기 때문이다.
화면 지우기 정도만 ANSI를 쓰고, 이것도 설정에서 끌 수 있게 한다.

**"저장" 메뉴가 없다.** 모든 설정은 값을 확정하는 즉시 Flash에 기록된다(17장).

브리지 메뉴에 있던 **`중계 제어`와 `프레임 주입` 항목은 사라졌다.** 대신 탭 포트 설정에
**보레이트 자동 탐색**과 **방향 매핑**이 들어왔다.

### 14.1 메인

```

머리말의 `tap PASSIVE (RX only)` 는 **이 장비가 송신할 수 없다는 사실을 상시 표시**하는
자리다. 브리지 펌웨어와 하드웨어를 섞어 쓰다가 착각하는 것을 막는다.
`overflow` 가 머리말에 있는 이유는, 탭에서 이것이 유일한 유실 지표이기 때문이다(3장).

### 14.2 탭 포트 설정

```text
--- 탭 포트 설정 ----------------------------------------
                  포트1              포트2
   RX 핀           GPIO16             GPIO26
   Baud             9600               9600
   Format            8N1                8N1
   방향             CTRL               MAIN   (auto, 확정됨)
---------------------------------------------------------
  1) 포트1 RX 핀      5) 포트2 RX 핀
  2) 포트1 Baud       6) 포트2 Baud
  3) 포트1 Format     7) 포트2 Format
  4) 양쪽 동일하게 맞추기

  s) 보레이트 자동 탐색 (scan)
  d) 방향 매핑 (auto / swap / 수동)
  0) 뒤로
>
```

**핀 입력 검증** — TX 핀이 없으므로 브리지보다 규칙이 단순하다.

| 핀 | 판정 |
|---|---|
| 1, 3 | **거부.** UART0(이 콘솔)이 쓰는 핀 |
| 6 ~ 11 | **거부.** SPI 플래시 전용 |
| 34 ~ 39 | **허용.** 입력 전용 핀이지만 RX만 쓰므로 문제없다 |
| 0, 2, 5, 12, 15 | 경고 후 허용. 부팅 스트래핑 핀 |
| 16, 17 | 경고 후 허용. **PSRAM 탑재 보드(WROVER)에서는 사용 불가** |
| 그 외 | 허용 |

두 포트가 같은 핀을 쓰면 거부한다.
**입력 전용 핀(34~39)을 쓸 수 있게 된 것이 탭 방식의 부수적 이점**이다.
브리지에서는 TX에 못 써서 제약이 있었다.

**되돌리기 안전장치는 두지 않는다.** 브리지에서는 UART 설정을 잘못 바꾸면 믹서 통신이
끊겨 30초 롤백이 필요했지만, 탭에서 잘못된 설정의 결과는 **로그가 안 나오는 것뿐**이다.
UART0 콘솔은 115200 고정이고 GPIO 1·3은 거부되므로 메뉴는 항상 살아 있다.
잘못 바꿨으면 그냥 다시 바꾸거나 `scan` 을 돌린다.

### 14.3 Network 설정

```text
--- Network 설정 ----------------------------------------
   무선 모드   AP+STA
   AP  SSID    NMX1108_SNIFFER   상태  동작중  접속 1대
       IP      192.168.4.1       채널  6
   STA SSID    MyAccessPoint     상태  연결됨
       IP      192.168.0.42      RSSI  -58 dBm
   호스트명    nmx-sniffer       웹 UI on (:80)
---------------------------------------------------------
  1) 무선 모드 (OFF / STA / AP / AP+STA)
  2) AP 설정      (이름 / 비밀번호 / 채널 / IP)
  3) STA 설정     (SSID / 비밀번호 / IP)
  4) 주변 AP 스캔해서 고르기
  5) 호스트명
  6) 웹 UI (on/off, 포트)
  7) 지금 연결 / 끊기

  0) 뒤로
>
```

**무선 모드** — ESP32는 AP와 STA를 동시에 띄울 수 있다(`WIFI_AP_STA`).

| 모드 | 쓰임 |
|---|---|
| `OFF` | 무선 끔. 수집에 무선 부하를 전혀 주고 싶지 않을 때 |
| `STA` | 기존 공유기에 붙는다. 사내망에서 접속 |
| `AP` | 스스로 AP가 된다. 공유기가 없는 현장 |
| `AP+STA` (기본값) | 둘 다. 공유기에 붙으면서 AP도 유지 |

`AP+STA` 를 기본값으로 두는 이유는 **AP가 구조 통로**이기 때문이다.
STA 설정을 잘못 넣어 공유기에 못 붙어도, AP로는 항상 들어와 고칠 수 있다.

> **AP+STA의 제약.** ESP32는 무선이 하나뿐이라 AP와 STA가 **같은 채널을 써야 한다.**
> STA가 공유기(채널 N)에 붙는 순간 AP도 채널 N으로 따라 옮겨가고, 그때
> **AP에 붙어 있던 기기는 잠깐 끊겼다 다시 붙는다.** 메뉴의 AP 채널 설정은
> AP 단독 모드에서만 의미가 있다는 뜻이다. 이 동작을 화면에 명시한다.

**기본값**

| 항목 | 기본값 |
|---|---|
| 무선 모드 | `AP+STA` |
| AP 이름 (SSID) | **`NMX1108_SNIFFER`** |
| AP 비밀번호 | `nmx11088` (WPA2 최소 8자) — 19장 검토 항목 |
| AP IP | `192.168.4.1` |
| AP 채널 | 6 |
| 호스트명 | `nmx-sniffer` |
| 웹 UI | on, 포트 80 |

> **AP 비밀번호를 왜 기본으로 거는가.** 탭 방식이라 접속자가 장비를 조작할 수는 없지만,
> **오가는 제어 트래픽이 그대로 보인다.** 방송 현장의 운용 내역이 전파 닿는 범위에
> 공개되는 셈이다. 기본 비밀번호는 이 문서에 적혀 있으니 **현장 투입 전에 반드시 바꾼다.**

**기타**

- 연결은 **비동기**로 한다. `WiFi.begin()` 후 상태만 폴링하고, 연결될 때까지 기다리며
  루프를 막지 않는다.
- 비밀번호는 화면에 `****` 로만 보여준다.
- 스캔은 수백 ms 동안 무선을 점유하고 AP 접속도 끊길 수 있으므로, 실행 전에 확인받는다.
- SSID는 최대 32자, 비밀번호는 최대 63자다.

### 14.4 RAW 스트림 보기

```text
--- RAW 스트림 --- [space]정지 [d]방향 [c]지우기 [ESC]나가기 ---
 00:12:03.114  C>M   AB 09 00 00 01 4A    |......J|
 00:12:03.240  M>C   AA D2 55 01 02 2A    |...U..*|
 00:12:03.902  C>M   AB 0B 00 00 02 47    |.......|
```

- HEX와 ASCII를 나란히 보여준다.
- `d` 로 방향 필터: 양방향 / `C>M` 만 / `M>C` 만.
- `space` 로 화면을 멈춰도 **수집은 계속된다.** 화면만 정지한다.

### 14.5 Unresolved 패킷

```text
--- Unresolved 패킷 (7/10) ------------------------------
  #  시각          방향  사유           데이터
  1  00:12:03.114  C>M   UNKNOWN_CMD    AB 7E 00 00 01 D5
  2  00:11:58.902  M>C   BAD_CHK        AA D3 55 02 04 7C   exp 26
  3  00:11:40.021  C>M   OUT_OF_RANGE   AB 05 00 00 2A 25   EFFECT RAW 0x2A?
  4  00:10:02.550  C>M   INCOMPLETE     AB 09 00
  5  00:09:58.113  M>C   ORPHAN         31 42 09
---------------------------------------------------------
  1~9) 상세 보기   x) 비우기   e) 텍스트 덤프   0) 뒤로
>
```

상세 보기에서는 해당 패킷의 바이트별 해석, 계산한 체크섬, 전후 200ms 동안
오간 프레임을 함께 보여준다. **어떤 버튼을 눌렀을 때 나온 미해독 패킷인지** 맞추는 것이
NMX-1108 분석의 핵심이기 때문이다.

### 14.6 패킷 상태 / 통계

```text
--- 패킷 상태 -------------------------------------------
                        C>M (port1)     M>C (port2)
  bytes                     12340            8210
  overflow                      0               0
  frames                     2056            1368
  chk OK / BAD            2053 / 3        1368 / 0
  unknown cmd                   2               0
  resync / incomplete        1 / 0           0 / 0
  skipped bytes                 0               0
  마지막 프레임            0.4초 전        0.9초 전
  프레임 평균 간격           612 ms         1004 ms
---------------------------------------------------------
  CMD 히스토그램                C>M      M>C
    0x09  PGM_CH                412        0
    0x0B  NEXT_CH               298        0
    0xD2  STATUS_PGM_PVW        300      300
    0xD3  STATUS_EFFECT         300      300
    0x7E  (unknown)               2        0
---------------------------------------------------------
  r) 초기화   0) 뒤로
```

브리지의 `bytes / relayed` 자리를 **`overflow`** 가 대신한다.
이 값이 0이 아니면 그 구간에서 바이트를 놓쳤을 수 있다는 뜻이고, 통계 전체의 신뢰도가 떨어진다
(정확한 유실 바이트 수는 알 수 없다. 3장 참조).

**CMD 히스토그램**은 어떤 명령이 실제로 쓰이는지를 한눈에 보여주고([ToDo.md](ToDo.md) C-5),
**프레임 평균 간격**은 컨트롤러의 폴링 주기를 자동으로 답해준다([ToDo.md](ToDo.md) C-2).

### 14.7 System / Factory reset

```text
--- System ----------------------------------------------
   펌웨어    v3.0            uptime   01:23:45
   설정      정상 (v1)       free heap 210 KB
   리셋 사유 Power-on
---------------------------------------------------------
  1) 설정 텍스트로 덤프
  2) 장치 정보 자세히
  3) 재부팅

  9) Factory reset  — 모든 설정을 공장 기본값으로
  0) 뒤로
>
```

`9` 를 고르면 되돌릴 수 없으므로 두 단계로 확인한다.

```text
!! Factory reset
   아래 항목이 모두 공장 기본값으로 돌아가고 장치가 재부팅됩니다.
     - 탭 포트 RX 핀 / Baud / Format  -> GPIO16, GPIO26  9600 8N1
     - 방향 매핑                      -> auto (미확정 상태로)
     - AP 이름 / 비밀번호             -> NMX1108_SNIFFER / nmx11088
     - STA SSID / 비밀번호            -> (지워짐)
     - 무선 모드 / 웹 UI / 호스트명    -> AP+STA / on / nmx-sniffer
     - 로그 및 디버그 설정             -> 기본값

   진행하려면 RESET 을 그대로 입력하세요 (취소는 Enter)
>
```

- `y` 한 글자가 아니라 **`RESET` 전체를 입력**하게 한다. 메뉴를 빠르게 넘기다 실수로
  누르는 것을 막기 위해서다.
- 동작은 NVS 네임스페이스를 통째로 지우고(`Preferences.clear()`) 즉시 재부팅한다.
  부팅 시 `magic` 이 없으므로 기본값으로 초기화된다.
- **하드웨어 탈출구** — 설정이 손상돼 메뉴조차 못 쓰는 상황에 대비해,
  부팅 직후 3초 안에 BOOT 버튼(GPIO0)을 누르고 있으면 같은 동작을 하게 한다.

## 15. 웹 UI

AP 또는 STA로 접속해 브라우저에서 같은 기능을 쓴다. UART0 메뉴와 **같은 데이터를 보고
같은 설정을 바꾼다.** 한쪽에서 바꾼 값은 다른 쪽에도 즉시 반영된다.

### 15.1 접속 방법

| 경로 | 주소 |
|---|---|
| AP 접속 | `NMX1108_SNIFFER` 에 연결 후 `http://192.168.4.1` |
| STA 접속 | 공유기가 준 IP, 또는 `http://nmx-sniffer.local` (mDNS) |

AP 모드에서는 **캡티브 포털**을 띄운다. AP에 붙으면 브라우저가 자동으로 설정 페이지를
열어 주므로 IP를 외울 필요가 없다. (DNS 서버가 모든 질의를 `192.168.4.1` 로 돌린다)

### 15.2 화면 구성

```text
┌────────────────────────────────────────────────┐
│ NMX Passive Sniffer      PASSIVE (RX)  ● 정상  │
├────────────────────────────────────────────────┤
│ [상태] [RAW] [Unresolved] [탭포트] [Network] [Sys]│
├────────────────────────────────────────────────┤
│                                                │
│   C>M (port1)   bytes 12340   overflow 0       │
│   M>C (port2)   bytes  8210   overflow 0       │
│   chk BAD 3    unknown 2    unresolved 7       │
│                                                │
│   CMD 히스토그램                                │
│   0x09 PGM_CH   ████████████████  412          │
│   0xD2 STATUS   ████████████      300          │
│                                                │
└────────────────────────────────────────────────┘
```

| 탭 | 내용 | UART0 메뉴 대응 |
|---|---|---|
| 상태 | 통계, CMD 히스토그램, 링크 상태 | 14.6 |
| RAW | 실시간 바이트 스트림 (1초 폴링) | 14.4 |
| Unresolved | 미해독 패킷 목록 + 상세 | 14.5 |
| 탭포트 | RX 핀 / Baud / Format / scan / 방향 | 14.2 |
| Network | 무선 모드 / AP / STA / 웹 UI | 14.3 |
| Sys | 장치 정보, 재부팅, **Factory reset** | 14.7 |

### 15.3 구현 방침

- **페이지는 자체 완결.** HTML·CSS·JS를 플래시에 넣어 서빙한다. AP 모드에는 인터넷이
  없으므로 CDN을 참조하면 화면이 깨진다. 외부 라이브러리를 쓰지 않고 순수 JS로 만든다.
- **실시간 갱신은 폴링.** `GET /api/status` 를 1초 주기로 부르고 JSON을 받는다.
  WebSocket은 나중으로 미룬다. 폴링이 단순하고, 1초면 관찰 용도로 충분하다.
- **RAW 탭만 예외적으로 빠르게.** 200~300ms 주기로 링버퍼의 새 바이트만 받아 이어붙인다.
  창을 벗어난 데이터는 서버 쪽 링버퍼가 덮어쓰므로, 놓친 구간은 표시해 준다.
- **설정 변경은 `POST /api/config`.** 받는 즉시 검증하고 Flash에 쓴다(17장).
  UART0 메뉴와 같은 검증 코드를 공유한다.
- **`/api/send` 는 만들지 않는다.** 이 브랜치는 하드웨어적으로 송신할 수 없으므로
  API를 두는 것 자체가 거짓말이 된다.

### 15.4 수집과의 관계

웹 서버가 `loop()` 를 오래 잡으면 RX 버퍼가 넘쳐 **바이트를 잃는다.**
장비는 멀쩡하지만 로그에 구멍이 나고, 탭에서는 그 구멍을 메울 방법이 없다.

그래서 v3에서 **수집을 전용 FreeRTOS 태스크로 분리**한다(18장).
웹 서버와 메뉴는 `loop()` 에 남고, 수집은 별도 태스크에서 돌기 때문에
페이지를 아무리 많이 열어도 바이트를 놓치지 않는다.

| | v2 (현재) | v3 |
|---|---|---|
| 수집 | `loop()` 폴링 | **전용 태스크** (코어 1, 높은 우선순위) |
| 로그·메뉴 | `loop()` | `loop()` |
| 웹 서버 | 없음 | `loop()` 또는 비동기 |
| WiFi 스택 | 없음 | 코어 0 |

## 16. Unresolved 패킷의 정의

"해석하지 못했다"를 명확히 해 둬야 버퍼에 무엇이 쌓일지 결정된다. 아래 6종으로 잡는다.

| 사유 | 조건 | 왜 중요한가 |
|---|---|---|
| `BAD_CHK` | 체크섬 불일치 | 프레임 구조나 보레이트/패리티 가정이 틀렸을 신호 |
| `UNKNOWN_CMD` | CMD가 NMX-1106 문서에 없음 | **NMX-1108 전용 명령 후보** |
| `OUT_OF_RANGE` | CMD는 알지만 데이터가 문서 범위 밖 (`EFFECT RAW 0x..?`, `SETUP KEY 0x..?` 등) | CH7/CH8 같은 확장값 후보 |
| `INCOMPLETE` | 6바이트가 차기 전에 50ms 이상 끊김 | 프레임 길이 가정이 틀렸을 신호 |
| `ORPHAN` | 헤더 없이 흘러다닌 바이트 (`SKIP`) | 동기 문제 또는 다른 프레임 구조 |
| `OVERFLOW` | RX 버퍼 포화 감지 | **탭 전용.** 통계 신뢰도가 깨진 구간의 표시 |

`PGM CH 7?` 처럼 **`?` 가 붙은 추정 디코딩은 unresolved로 넣지 않는다.**
해석 자체는 됐고 확증이 없을 뿐이라 양이 많아 버퍼를 밀어내기 때문이다.
대신 통계에 `추정 디코딩` 카운터를 따로 둔다.

**저장 위치** — 링버퍼는 RAM에 둔다. 기본 10개, 설정에서 최대 32개까지.
재부팅하면 사라지는데, Flash에 쓰면 수명이 닳고 잡음이 심할 때 쓰기가 폭주하기 때문이다.
필요하면 `e) 텍스트 덤프` 로 화면에 뽑아 복사해 둔다.

> 설정값은 변경 즉시 Flash에 쓰지만(17장), **패킷 데이터는 절대 쓰지 않는다.**
> 설정 변경은 사람이 하는 일이라 평생 수백 번이지만, 패킷은 초당 수십 개씩 들어온다.

## 17. 설정 영속화

ESP32 Arduino의 **Preferences**(NVS) 를 쓴다. 구조체를 통째로 `putBytes` 로 저장한다.
키를 하나씩 저장하지 않는 이유는 갱신이 원자적이고 버전 관리가 쉽기 때문이다.

```cpp
struct Config {
    uint32_t magic;        // 'NMX1' 손상/미초기화 판별
    uint16_t version;      // 구조 변경 시 마이그레이션
    uint16_t size;

    struct Tap {
        int8_t   rxPin;    // TX 핀 없음 — 패시브 탭
        uint32_t baud;
        uint8_t  format;   // 0=8N1 1=8E1 2=8O1 3=7E1 4=7O1 5=8N2
    } tap[2];              // [0]=포트1 [1]=포트2

    uint8_t  dirMode;      // 0=auto 1=수동
    uint8_t  dirPort1;     // 0=미확정 1=CTRL 2=MAIN

    uint8_t  wifiMode;     // 0=OFF 1=STA 2=AP 3=AP+STA
    char     ssid[33];
    char     pass[65];
    uint8_t  staUseDhcp;
    uint32_t staIp, staGw, staMask, staDns;

    char     apSsid[33];        // 기본값 "NMX1108_SNIFFER"
    char     apPass[65];        // 기본값 "nmx11088"
    uint8_t  apChannel;         // 기본값 6
    uint32_t apIp;              // 기본값 192.168.4.1

    char     hostname[33];      // 기본값 "nmx-sniffer"
    uint8_t  webEnabled;        // 기본값 on
    uint16_t webPort;           // 기본값 80

    uint8_t  frameLogEnabled;
    uint8_t  rawLogEnabled;
    uint8_t  unresolvedDepth;   // 기본 10, 최대 32
    uint8_t  ansiEnabled;

    uint32_t crc32;        // 위 전체의 체크섬
};
```

브리지 버전에 있던 `txPin`, `uartBackup[2]`, `uartPending`, `tcpPort` 는 없앴다.
TX가 없고, 롤백이 필요 없고(14.2), 주입용 TCP 포트를 쓸 일이 없기 때문이다.

**`dirPort1` 을 저장하는 이유** — 자동 판정은 트래픽이 있어야 동작한다. 장비가 조용한
상태로 부팅하면 한동안 `[P1?]` 로 찍힌다. 한 번 확정한 매핑을 저장해 두면 다음 부팅부터
바로 `[C>M]` 로 나온다. 배선을 바꿨다면 `dir auto` 로 다시 잡게 하거나 `dir swap` 을 쓴다.

### 17.1 저장 시점 — 변경 즉시

**"저장" 메뉴는 없다.** 값이 확정되는 순간 Flash에 기록한다.
UART0 메뉴에서 바꾸든 웹 UI에서 바꾸든 같다.

| 입력 종류 | 저장 시점 |
|---|---|
| 숫자·항목 선택 (Baud, 모드, on/off …) | 고른 즉시 |
| 문자열 입력 (SSID, 비밀번호, 호스트명) | **Enter로 필드를 확정할 때.** 한 글자마다 쓰지 않는다 |
| 방향 자동 판정 결과 | 확정된 순간 1회 |
| `scan` 결과 | 사용자가 `apply` 를 승인했을 때 |

저장에 성공하면 화면에 `saved` 를 짧게 표시한다. 실패하면 이유를 남긴다.

### 17.2 플래시 수명

값 하나 바꿀 때마다 구조체 전체를 다시 쓰는 방식이라 낭비처럼 보이지만, 실제로는 문제가 없다.

- NVS는 **자체 wear leveling** 을 한다. 같은 물리 섹터를 반복해서 지우지 않는다.
- 플래시 섹터 내구성은 보통 10만 회 수준이다.
- 설정 변경은 **사람이 메뉴를 조작할 때만** 일어난다. 하루에 100번씩 바꿔도 수년치다.

**주의할 것은 `scan` 이다.** 후보를 훑는 동안 매번 저장하면 한 번 실행에 수십 회를 쓴다.
그래서 스캔 중에는 저장하지 않고, **채택된 최종 값만 한 번 쓴다.**

반면 **패킷 데이터는 절대 Flash에 쓰지 않는다.** 초당 수십 개씩 들어오므로
같은 방식으로 저장하면 금세 수명을 태운다. Unresolved 링버퍼가 RAM에 있는 이유다(16장).

### 17.3 잘못된 값이 굳는 문제

즉시 저장의 위험은 **틀린 값도 즉시 굳는다**는 점이다. 다만 탭 방식에서는 결과가
"로그가 안 나온다"뿐이라 브리지만큼 심각하지 않다.

1. **입력 검증.** 핀 번호, IP 형식, SSID 길이, 비밀번호 최소 8자 등을 저장 **전에** 거른다.
   통과하지 못한 값은 아예 쓰지 않는다.
2. **AP는 항상 살아 있다.** STA 설정을 아무리 잘못 넣어도 AP로 들어와 고칠 수 있고,
   무선을 통째로 꺼도 **UART0 콘솔은 115200 고정**이라 항상 접근 가능하다.
   그래도 안 되면 Factory reset(14.7).
3. **탭 포트 설정은 `scan` 으로 복구.** 보레이트를 잘못 굳혔어도 `scan` 한 번이면 되찾는다.

**손상 대응** — `magic` 이나 `crc32` 가 맞지 않으면 기본값으로 부팅하고 그 사실을 알린다.
`version` 이 낮으면 마이그레이션한다.

**비밀번호 보관** — NVS는 기본적으로 암호화되지 않는다. 플래시를 덤프하면 WiFi 비밀번호와
AP 비밀번호가 평문으로 보인다. 이 장비의 용도상 과하다고 보고
**암호화 없이 가되, 문서에 명시**하는 쪽을 택했다.

## 18. 수집 무결성 원칙

메뉴가 아무리 화려해도 **바이트를 놓치면 실패**다.
탭에서는 놓친 바이트를 되돌려 받을 방법이 없다.

### 18.1 수집을 전용 태스크로 분리

v2는 `loop()` 안에서 UART 버퍼를 폴링한다. `loop()` 가 하는 일이 로그 출력뿐일 때는
이걸로 충분했지만, v3에서는 메뉴 렌더링·WiFi·웹 서버가 같은 `loop()` 에 들어온다.
HTTP 요청 하나가 수십 ms를 잡아먹는 사이 RX 버퍼가 넘칠 수 있다.

```text
코어 0                          코어 1
┌─────────────────┐            ┌──────────────────────────┐
│ WiFi / TCP 스택 │            │ captureTask (우선순위 높음)│
│ (ESP-IDF)       │            │   uart_read_bytes() 대기  │
└─────────────────┘            │   → 링버퍼에 적재         │
                               ├──────────────────────────┤
                               │ loopTask   (우선순위 1)   │
                               │   파서 / 메뉴 / 웹 / 로그 │
                               └──────────────────────────┘
```

- `captureTask` 는 `uart_read_bytes()` 에서 **블로킹 대기**한다. 데이터가 없으면 CPU를
  전혀 쓰지 않고, 바이트가 오면 즉시 깨어나 링버퍼에 넣는다.
- 우선순위를 `loopTask` 보다 높게 두어, 웹 요청을 처리하는 중이라도 **선점**한다.
- **파싱·통계·로그는 수집 경로에서 뺀다.** 수집 태스크는 옮겨 담는 일만 한다.
  파서가 느려도 바이트가 유실되지 않게 하기 위해서다.
- 링버퍼가 넘치면 `OVERFLOW` 로 기록한다. **조용히 넘기지 않는다.**

### 18.2 나머지 원칙

1. **메뉴 출력은 논블로킹 큐로.** 화면 한 장을 `Serial.print` 로 한 번에 쏟지 않고,
   출력 대기열에 넣어 `availableForWrite()` 만큼씩 흘려보낸다.
2. **WiFi 작업은 비동기로.** 연결·스캔에서 블로킹 호출을 쓰지 않는다.
   스캔은 무선을 오래 점유하고 AP 접속도 끊으므로 사전 확인을 받는다.
3. **웹 페이지는 가볍게.** 자체 완결 단일 페이지, 폴링 주기 1초.
   응답 JSON은 작게 유지한다.
4. **포트 재설정은 짧게.** `end()` → `begin()` 사이에 수신이 끊기므로,
   그 순간 진행 중이던 프레임은 유실된다. 유실 사실을 로그에 남긴다.
5. **`overflow` 를 상시 표시.** 메뉴 머리말과 웹 상단에 항상 띄운다.
   브리지의 `bytes == relayed` 를 대신하는 유일한 자기 검증 지표다.
6. **메뉴 진입이 수집을 멈추지 않는다.** 화면 출력만 멈추고 파서·통계·링버퍼는 계속 돈다.

# 4부. 코드 반영 현황

## 20. 브리지 코드에서 무엇이 바뀌었나

[../src/](../src/) 는 브리지 구현에서 패시브 탭(`v2.1.0-tap`)으로 전환을 마쳤다.
[../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) 와
[../src/nmx_selftest.cpp](../src/nmx_selftest.cpp) 는 연결 방식과 무관하므로 손대지 않았다.

### 20.1 걷어낸 것

| 대상 | 이유 |
|---|---|
| 중계 `write()` 경로 전체 | 탭에서는 반대편으로 내보내지 않는다 |
| `relay on` / `relay off` | 중계가 없으므로 무의미 |
| `inject on` / `inject off`, `sendmain`, `sendctrl` | TX가 연결되지 않아 동작할 수 없다 |
| TX 핀 정의 (`CTRL_TX_PIN`, `MAIN_TX_PIN`) 및 부팅 시 idle 고정 | 출력 핀을 아예 잡지 않는다 |
| `stats` 의 `relayed` 카운터 | `overflow` 로 대체 |

### 20.2 바꾼 것

| 대상 | 변경 |
|---|---|
| `Serial1/2.begin()` | TX 인자에 `-1` 을 넘겨 출력 핀 미할당 |
| 로그 헤더 | `[CTRL->MAIN]` → 고정 폭 `[C>M]` / `[M>C]` / `[P1?]` (4.1) |
| 포트 명명 | `CTRL`/`MAIN` 고정 → `port1`/`port2` + 방향 매핑 (4.2) |
| 핀 매크로 | `CTRL_RX_PIN`·`MAIN_RX_PIN` → `TAP1_RX_PIN`·`TAP2_RX_PIN` |
| RX 버퍼 | `setRxBufferSize(512)` 를 재설정 때마다 다시 적용 |

> **`txPin = -1` 이 실제로 무엇을 하는가.** ESP32 Arduino 코어의 `_uartAttachPins()` 는
> `txPin >= 0` 일 때만 핀을 연결한다. 기본 핀 폴백은 `rxPin` 과 `txPin` 이 **둘 다** 음수일
> 때만 걸리므로, RX 핀을 지정하고 TX에 `-1` 을 주면 **출력 핀이 아예 라우팅되지 않는다.**
> 브리지 펌웨어에 있던 부팅 시 TX idle 고정(`pinMode`/`digitalWrite`)이 사라진 것도
> 이 때문이다. 잡을 출력 핀 자체가 없다.

### 20.3 더한 것

| 대상 | 내용 |
|---|---|
| 방향 자동 판정 | 헤더 바이트 통계 + `dir` 명령군 (4.2) |
| 보레이트/형식 런타임 변경 | `baud`, `format` 및 포트별 변형 (5.1) |
| 보레이트 자동 탐색 | `scan`, `scan full` (5.2) |
| 오버플로 검출 | 카운터 + `OVERFLOW` 로그 (3장, 4.3) |
| 브리지 명령 안내 | `relay`·`inject`·`sendmain`·`sendctrl` 입력 시 "RX 전용이라 송신 불가" 안내 |

`platformio.ini` 의 핀 오버라이드 주석도 `TAP1_RX_PIN` / `TAP2_RX_PIN` 두 개로 줄였다.

## 21. 남은 구현 단계

1~4단계는 완료했고 **실측 검증이 남았다.** 5단계 이후는 편의 기능이므로
실측이 시작된 다음에 해도 늦지 않다.

| 단계 | 내용 | 검증 | 상태 |
|---|---|---|---|
| 1 | **탭 전환** (20.1 / 20.2) — 송신 제거, RX 전용화 | ESP32 전원을 뽑아도 믹서가 멀쩡한지. 프레임이 양쪽에서 잡히는지 | 구현 완료 / **실측 대기** ([ToDo.md](ToDo.md) A-6·A-2) |
| 2 | 방향 자동 판정 + `dir` 명령군 | 탭선을 일부러 바꿔 꽂아도 라벨이 맞게 붙는지 | 구현 완료 / **실측 대기** (A-2) |
| 3 | 보레이트/형식 런타임 변경 + `scan` | 9600을 모른다고 가정하고 `scan` 만으로 찾아내는지 | 구현 완료 / **실측 대기** (A-3) |
| 4 | 오버플로 검출 | 일부러 긴 출력을 반복해 `overflow` 가 실제로 잡히는지 | 구현 완료 / **실측 대기** (A-5) |
| 5 | 수집을 전용 태스크로 분리 (18.1) | 기존 기능 그대로, `overflow` 0 유지 | 미구현 |
| 6 | Config 구조체 + NVS 즉시 저장 + Factory reset | 값 바꾸고 바로 전원 차단 → 재부팅 시 유지 | 미구현 |
| 7 | 메뉴 프레임워크 (모드 전환, 논블로킹 출력 큐) | 메뉴 조작 중 `overflow` 0 유지 | 미구현 |
| 8 | 탭 포트 / Debug 메뉴 | 3~4단계 기능을 메뉴로 재현 | 미구현 |
| 9 | Network 메뉴 + 비동기 WiFi | WiFi 켠 상태로 `overflow` 0 유지 | 미구현 |
| 10 | 웹 UI | 여러 브라우저로 동시 접속하며 `overflow` 0 유지 | 미구현 |

**1~4단계를 먼저 둔 이유** — 이 네 가지가 이 브랜치의 존재 이유이자,
장비에 붙여 실제 데이터를 받아보기 위한 최소 조건이다.

> **5단계(수집 태스크 분리)가 아직 필요 없는 이유.** 지금은 `loop()` 가 수집과 로그만
> 하므로 `overflow` 가 뜰 일이 거의 없다. WiFi와 웹 서버가 같은 `loop()` 에 들어오는
> 6단계 이후부터 실질적인 문제가 된다. 다만 `scan` 실행 중에는 콘솔 입력을 받지 않으므로
> (중단 키 감지만 한다) 그 점은 알고 쓴다.

# 5부. 이후 계획

## 22. 관찰 이후

프로토콜이 확정되면 제어 디바이스로 넘어간다. 그 시점에 **연결 방식을 다시 브리지로
바꿔야 한다.** 탭으로는 프레임을 쏠 수 없기 때문이다.

- **브랜치를 나눠 두는 이유가 이것이다.** 관찰은 `sniffingOnly`, 제어는 브리지 계열로
  가고, 프로토콜 정의(`nmx_protocol.*`)와 디코더는 양쪽이 공유한다.
- **디코더와 통계 구조는 그대로 재사용한다.** 연결 방식이 바뀌어도 프레임 해석은 같다.
- **탭에서 확인 불가능한 항목**([ToDo.md](ToDo.md) F절)은 브리지로 옮긴 뒤
  **실사용이 아닌 장비**에서 수행한다.

## 23. 그 이후 아이디어

1. CSV 로그 출력 (`ts_ms,dir,hex,chk,decoded`) — 오프라인 분석용
2. 버튼 이벤트별 자동 라벨링
3. WebSocket 기반 실시간 상태 모니터링
4. SD 카드 로그 저장 — 장시간 무인 캡처. 탭이라 장비에 붙여두고 방치할 수 있다
5. Wi-Fi 웹 UI를 통한 영상믹서 제어 (브리지 전환 필요)
6. ESP32가 컨트롤러를 완전히 대체하는 standalone controller 모드

## 부록 A. 설계 변경 이력

| 버전 | 변경 | 이유 |
|---|---|---|
| v1 | 수동 감청(passive tap). RX만 연결, TX는 UART에 할당조차 안 함 | 장비 통신에 영향을 주지 않는 것이 최우선이었다 |
| v2 | 브리지(중계) 방식으로 전환. 원래 케이블을 끊고 ESP32가 통로가 된다 | 최종 목표가 네트워크 기반 제어 디바이스이므로, 주입 경로를 미리 갖춰 두는 편이 낫다고 판단 |
| v2 | 빌드 환경을 `esp32dev` 하나로 통합. `ENABLE_INJECTION` 매크로 폐지 | 브리지에서는 TX가 기본으로 연결되므로 컴파일 타임 분기가 무의미해졌다 |
| **v2-tap** (이 브랜치) | **패시브 탭(커플링)으로 복귀.** 원래 케이블을 유지한 채 RX 2가닥만 병렬로 얹는다 | 관찰 단계에서 실사용 중인 장비를 멈추지 않기 위해서다. 제어는 프로토콜 확정 후 별도 브랜치에서 한다 |
| **v2-tap** | **보레이트·프레임 형식 런타임 변경 + `scan` 자동 탐색** | 통신 파라미터가 미확정인데 탭에서는 틀려도 무해하므로, 재빌드 없이 시도하는 편이 훨씬 빠르다 |
| **v2-tap** | **방향 자동 판정(`0xAB`/`0xAA`)과 고정 폭 방향 헤더** | 배선이 곧 방향이던 브리지와 달리, 탭에서는 배선만으로 방향을 알 수 없다 |
| v3 (설계) | UART0 메뉴 + 설정 영속화 + WiFi | 재빌드 없이 설정을 바꾸고, 분석에 필요한 정보를 화면으로 정리해서 본다 |

**v1과 v2-tap의 차이** — 둘 다 패시브 탭이지만, v1은 보레이트가 컴파일 타임 고정이었고
방향은 배선 순서를 믿었다. v2-tap은 **둘 다 런타임에 해결**한다.
프로토콜 파라미터가 미확정인 상태에서 관찰을 시작해야 하므로, 재빌드 횟수를 줄이는 것이
곧 분석 속도다.
