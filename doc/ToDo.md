# NMX-1108 미확인 항목 및 실측 계획

이 펌웨어의 프로토콜 해석은 **NMX-1106 문서**를 근거로 한 것이고, NMX-1108에서 확장·변경된
부분은 아직 추정이다. 추정 구간은 로그에 `?` 가 붙어 나오므로, 아래 항목을 실측해서 확정한다.

- 상태 표기: `[ ]` 미확인 / `[x]` 확정
- 우선순위: **P0** 다른 항목의 전제 / **P1** 8채널 확장 핵심 / **P2** 부가 확인
- 각 항목의 `기록:` 칸에 실제 관찰한 프레임을 적어 둔다.

관련 파일: [README.md](README.md) · [../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) · [NMX-1106_통신 프로토콜.txt](NMX-1106_통신%20프로토콜.txt)

## A. 선행 확인 (장비 연결 전/직후)

### [ ] A-1. 디코더 selftest 통과 — **P0**

개발 PC에 호스트 C++ 컴파일러가 없어 디코딩 문자열은 실행 검증을 하지 못했다.
보드에서 한 번은 반드시 돌려야 한다.

**테스트 조건**
1. 장비 연결 없이 ESP32만 USB로 연결
2. `pio run -e esp32dev -t upload` 후 `pio device monitor`
3. 시리얼 모니터에 `selftest` 입력

**판정**
- `SELFTEST PASSED: 47/47 cases passed` → 통과
- `FAIL` 줄이 나오면 해당 케이스의 `got` / `want` 를 보고
  [../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) 수정

### [ ] A-2. 배선 방향 및 중계 성립 — **P0**

RJ45 핀어사인(4=GND, 5=RxD, 6=TxD)은 **장비 포트 기준 표기일 가능성이 높다.**
중계 방식에서는 방향을 틀리면 믹서가 아예 동작하지 않으므로, **믹서가 정상 동작하는 것 자체가
배선이 맞다는 증거**가 된다.

**테스트 조건**
1. 원래 컨트롤러-본체 케이블을 제거하고 ESP32를 중간에 넣는다 ([README.md](README.md) 2절 배선)
2. 본체 → 컨트롤러 → ESP32 순으로 전원을 넣는다
3. 컨트롤러에서 PGM CAM1 버튼을 누른다

**판정**

| 관찰 | 해석 | 조치 |
|---|---|---|
| 믹서가 CH1로 전환 + `[CTRL->MAIN] AB 09 00 00 01 4A` | 배선·중계 모두 정상 | 확정 |
| 로그는 나오는데 믹서가 반응 안 함 | 수신은 되지만 **송신 경로가 틀림** | MAX3232 #2 의 T1OUT → 본체 RxD 연결 확인 |
| 로그에 `AA` 로 시작하는 프레임이 `CTRL->MAIN` 으로 나옴 | **두 MAX3232가 서로 바뀜** | 배선 교환 또는 `CTRL_RX_PIN`↔`MAIN_RX_PIN`, `CTRL_TX_PIN`↔`MAIN_TX_PIN` 교환 |
| 아무 로그도 없음 | 라인 오선택 | 오실로스코프/로직 분석기로 신호 있는 핀을 다시 찾는다 |

`relay off` → 버튼 눌러도 믹서 무반응 → `relay on` → 다시 반응, 이 순서로 확인하면
중계가 실제로 ESP32를 거쳐 가는지 확실해진다.

**기록:**

### [ ] A-3. 통신 파라미터 8N1 — **P0**

문서에 `9600BPS, 1STOP` 만 있고 데이터 비트/패리티는 명시가 없어 `8N1` 로 가정했다.

**테스트 조건**
1. A-2 통과 상태에서 PGM CAM1 버튼을 누른다
2. 기대값 `AB 09 00 00 01 4A` 와 한 바이트도 틀리지 않는지 확인

**판정**
- 정확히 일치하고 `CHK=OK` → 8N1 확정
- 바이트가 깨지거나 `CHK=BAD` / `SKIP` / `INCOMPLETE` 가 반복 → 패리티 가정이 틀렸다.
  `raw on` 으로 바꿔 원시 바이트를 보고, `SERIAL_8E1` / `SERIAL_8O1` / `SERIAL_7E1` 순으로
  [../src/main.cpp](../src/main.cpp) 의 `Serial1.begin()` 인자를 바꿔가며 재시도
- 아예 다른 보레이트로 의심되면 4800 / 19200 도 시도

**기록:**

### [ ] A-4. 프레임 길이 6바이트 고정 — **P1**

1106 문서의 예제는 전부 6바이트다. 1108에서 8채널용으로 길이가 늘어났을 수 있다.

**테스트 조건**
1. 버튼을 하나씩 천천히 누르며 10분 정도 로그를 받는다
2. `stats` 로 `incomplete` / `skipped bytes` / `chk BAD` 를 확인

**판정**
- 세 값이 모두 0에 가까움 → 6바이트 고정 확정
- `skipped bytes` 나 `chk BAD` 가 프레임 수에 비례해서 늘어남 → **길이가 6이 아니다.**
  `raw on` 으로 전환해 헤더(`AB`) 사이의 실제 바이트 수를 세고
  [../include/nmx_protocol.h](../include/nmx_protocol.h) 의 `FRAME_LEN` 을 조정

**기록:**

### [ ] A-5. 중계 무결성 — **P0**

ESP32가 통로가 된 이상, 한 바이트라도 흘리면 믹서가 오작동한다.

**테스트 조건**
1. `clear` 로 통계 초기화
2. 버튼을 빠르게 연타하고, 페이더도 빠르게 왕복시킨다 (트래픽을 일부러 몰아준다)
3. `raw on` 으로 로그량을 두 배로 늘린 뒤 2번을 반복
4. `stats` 확인

**판정**
- `bytes` == `relayed` (양방향 모두) → 유실 없음. 확정
- `bytes` > `relayed` → 중계 누락. `relay off` 상태였는지 먼저 확인
- `dropped log lines` 가 늘어남 → **정상 동작이다.** 로그를 버려서 중계를 지킨 것.
  다만 그만큼 관찰 기록이 비므로, 분석 중에는 `raw off` 로 로그량을 줄인다
- 조작 중 믹서가 버벅이거나 엉뚱하게 반응 → 중계 지연 의심. `frame off` `raw off` 로
  로그를 최소화하고 재현되는지 확인

### [ ] A-6. 전원 차단 시 동작 확인 — **P1**

브리지의 가장 큰 위험은 ESP32가 죽으면 믹서 조작이 멈춘다는 점이다.
실사용 전에 그 상황을 미리 겪어 본다.

**테스트 조건**
1. 정상 중계 상태에서 ESP32의 USB를 뽑는다
2. 컨트롤러 버튼을 눌러 본다
3. USB를 다시 꽂고 부팅 완료 후 다시 눌러 본다

**판정**
- 전원 차단 중 무반응 → 예상된 동작. **되돌릴 원래 케이블을 항상 옆에 둔다**
- 재부팅 후 정상 복귀되는지, 부팅 순간 믹서가 오동작하지 않는지 확인
  (펌웨어가 TX 핀을 idle High로 먼저 고정하므로 글리치는 없어야 한다)
- 부팅 순간 믹서가 엉뚱하게 반응하면 → 전원 인가 순서를 바꾸거나
  MAX3232 T_IN 에 풀업을 검토

**기록:**

## B. 8채널 확장 (NMX-1108 핵심)

### [ ] B-1. PGM CH7 / CH8 명령 프레임 — **P1**

1106은 `D3` 에 채널 번호를 그대로 싣는다(`01`~`06`). 7/8이 같은 규칙인지 미확인.

**추정값**

```text
AB 09 00 00 07 44   PGM CH7
AB 09 00 00 08 43   PGM CH8
```

**테스트 조건**
1. PGM CH1 → CH2 → ... → CH8 순서로 하나씩 누른다 (각 1초 간격)
2. `[CTRL->MAIN]` 프레임을 순서대로 기록

**판정**
- `PGM CH 7?` / `PGM CH 8?` 로 디코딩되면 추정 적중 →
  [../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) 의 `describeChannelSelect()` 에서
  `d3 <= 8` 분기의 `?` 표시를 제거
- 다른 CMD(예: `0x0A`)나 다른 `D3` 값이 나오면 실제 값으로 디코더 수정
- `CHK=BAD` 가 뜨면 체크섬 식이 확장 명령에서 다를 수 있다 → `expected CHK=` 값과 비교

**기록:**

|---|---|
| PGM CH1 | |
| PGM CH6 | |
| PGM CH7 | |
| PGM CH8 | |
| PGM OFF | |

### [ ] B-3. D2 응답의 CH7/CH8 표현 — **P1** (가장 불확실)

1106의 `D2` 응답은 **비트마스크**다. `0x01`=CH1 … `0x20`=CH6, 그리고 `0x40`=**OFF**.
8채널로 늘리면 CH7/CH8이 들어갈 자리가 `0x40`/`0x80` 인데 `0x40` 은 이미 OFF가 쓰고 있다.
즉 **OFF 코드가 바뀌었거나, CH7/CH8이 다른 방식으로 실린다.**

펌웨어는 이 모호함을 로그에 그대로 노출한다.

| 관찰값 | 로그 표기 |
|---|---|
| `0x40` | `OFF\|CH7?` |
| `0x80` | `CH8?` |
| `0x00` | `NONE` |

**테스트 조건**

본체가 `AB D2 00 00 01 81` 요청에 응답하는지부터 확인해야 한다(C-1 선행).
응답이 확인되면 아래 순서로 하나씩 바꾸며 `[MAIN->CTRL] AA D2 55 xx yy` 의
`xx`(PGM) / `yy`(PVW) 를 기록한다.

1. PGM CH1 선택 → 응답 기록
2. PGM CH6 선택 → 응답 기록
3. **PGM CH7 선택 → 응답 기록** ← 핵심
4. **PGM CH8 선택 → 응답 기록** ← 핵심
5. **PGM 전체 OFF → 응답 기록** ← 핵심
6. PVW 에 대해 1~5 반복

**판정**
- CH7에서 `0x40`, OFF에서 `0x40` 이 **아닌** 값 → CH7=`0x40`, CH8=`0x80`, OFF는 새 코드.
  `formatChannelMask()` 의 `CH_MASK_OFF` 분기를 새 OFF 코드로 교체
- CH7에서 `0x40` 이 아닌 값이 나옴 → 비트마스크가 아니거나 바이트가 하나 더 늘었다.
  `xx yy` 외의 바이트(특히 `0x55` 자리)도 같이 변하는지 확인
- OFF에서 `0x40` 유지 + CH7에서 다른 값 → 1106 규칙 그대로 + CH7/CH8만 별도 인코딩

> C-6과 함께 보면 해석이 빨라진다. 이 바이트가 **램프 패턴**이라면 8채널에서는
> bit0~bit7을 CH1~CH8이 다 쓰게 되어 OFF가 들어갈 자리가 없다. 그렇다면 `0x55` 자리가
> 확장 바이트로 쓰였을 가능성이 높으므로, `xx yy` 만 보지 말고 **3번째 바이트도 같이 기록**한다.

**기록:**

| 상태 | PGM 바이트 | PVW 바이트 |
|---|---|---|
| CH1 | | |
| CH6 | | |
| CH7 | | |
| CH8 | | |
| OFF | | |

### [ ] B-4. D3 응답의 예약 비트 — **P2**

1106 문서에서 `BYTE_5` 의 bit4/bit5는 `Fixed 0` 이다. 1108에서 확장 플래그로 쓰였을 수 있다.
켜져 있으면 로그에 `(fixed-0 bits set: 0x..?)` 가 붙는다.

**테스트 조건**
1. EFFECT / CKEY / PIP / DSK / EXT AUDIO 를 하나씩 켜고 끄며 `AA D3` 응답을 기록
2. 어떤 조작에서도 안 변하는 비트가 있는지 대조

**판정**
- `fixed-0 bits set` 표시가 한 번도 안 뜸 → 1106과 동일. 확정
- 특정 조작에서 bit4/bit5가 켜짐 → 그 조작 이름을 디코더에 추가

**기록:**

## C. 동작 방식 및 기존 명령의 동일성

### [ ] C-1. 본체의 상태 조회 응답 여부 — **P1**

`AB D2 00 00 01 81` 요청에 NMX-1108 본체가 실제로 응답하는지 미확인. B-3의 전제다.

**테스트 조건**
1. 컨트롤러를 정상 연결한 상태로 로그를 받는다
2. `[CTRL->MAIN] ... AB D2 ...` 직후 `[MAIN->CTRL] ... AA D2 ...` 가 따라오는지 본다

**판정**
- 요청-응답 쌍이 보임 → 확정. B-3 진행 가능
- `[CTRL->MAIN]` 만 있고 응답 없음 → 본체가 상태 조회를 지원하지 않거나,
  Serial2 배선/방향 문제. A-2 를 다시 확인
- 컨트롤러가 `D2` 요청 자체를 안 보냄 → `inject on` 후 `sendmain` 으로 직접 넣어봐야 한다(D-3)

**기록:**

### [ ] C-2. 컨트롤러의 주기적 폴링 여부 — **P2**

컨트롤러가 상태를 주기적으로 물어보는지에 따라, 나중에 ESP32가 컨트롤러를 대체할 때
폴링 루프를 흉내내야 하는지가 갈린다.

**테스트 조건**
1. 버튼을 **전혀 누르지 않은 상태**로 2분간 방치
2. `clear` 로 통계를 비운 뒤 다시 2분 방치하고 `stats`

**판정**
- `frames` 가 계속 늘어남 → 주기적 폴링 있음. 타임스탬프 간격으로 주기를 계산해 기록
- `frames` 가 0 → 이벤트 구동. 버튼을 눌렀을 때만 전송

**기록:** 폴링 주기 = ____ ms

### [ ] C-3. TAKE / CUT / FADER 동일성 — **P2**

**추정값** (1106 기준)

```text
AB 06 00 00 01 4D   FADER MODE TAKE
AB 06 00 00 02 4C   FADER MODE CUT
AB 07 00 D2 D3 CHK  Manual Fader, 값 = (D2<<8)|D3, 0x000~0x1FF
```

**테스트 조건**
1. TAKE 버튼, CUT 버튼을 각각 누른다
2. 수동 페이더를 **한쪽 끝에서 반대쪽 끝까지 천천히** 민다

**판정**
- `FADER MODE TAKE` / `FADER MODE CUT` 이 그대로 나오면 확정
- 페이더 로그의 값이 `FADER 0x000` → `FADER 0x1FF` 로 단조 증가하면 16비트 해석 확정
- 값이 `0x1FF` 를 넘거나 중간에 튀면 스케일이 다르다 → 실측 최대/최소를 기록

**기록:** 페이더 최소 = ____ , 최대 = ____

### [ ] C-6. 컨트롤러 램프를 누가 켜는가 — **P1**

버튼을 누르면 컨트롤러의 해당 램프에 불이 들어온다. 이것이 **컨트롤러가 스스로 켜는 것**인지,
**본체 회신을 받아서 켜는 것**인지 확정한다. 나중에 ESP32가 컨트롤러를 대체하거나
네트워크로 제어할 때 어느 쪽을 흉내내야 하는지가 여기서 갈린다.

**프로토콜에서 읽히는 정황** (본체가 몰아주는 쪽에 무게)

같은 CH3인데 명령과 응답의 인코딩이 다르다.

```text
명령  AB 09 00 00 03 48     ← 채널 번호 3 (그냥 숫자)
응답  AA D2 55 04 ..        ← 0x04 (비트마스크, bit2)
```

PGM은 한 번에 한 채널만 켜지므로 비트마스크일 이유가 없는데도 비트로 펼쳐져 있다.
게다가 비트 배치가 패널 버튼 수와 정확히 맞는다.

```text
bit0 CH1 / bit1 CH2 / bit2 CH3 / bit3 CH4 / bit4 CH5 / bit5 CH6 / bit6 OFF   = 7개 버튼 7비트
```

`0x40 = OFF` 가 **전용 비트**라는 점이 특히 그렇다. 순수한 상태값이라면 OFF는 `0x00` 이면
충분하다. 명령표에 `AB 09 00 00 00 4B PGM CH OFF` 가 있으니 패널에 OFF 버튼이 실재하고,
그렇다면 이 바이트는 **램프 패턴 그 자체**로 보인다.

반대로, 문서에는 **자발적(unsolicited) 응답 프레임이 없다.** 모든 `AA` 는 `AB D2`/`AB D3`
요청에 대한 "Return Value" 로만 나온다. 따라서 가능한 모델은 두 가지이고, 둘 다 문서와
모순되지 않는다.

| | 모델 A — 로컬 점등 | 모델 B — 폴링 후 점등 |
|---|---|---|
| 버튼 누름 | 컨트롤러가 즉시 자기 램프 점등 | 명령만 보냄 |
| 램프 갱신 | 로컬 | 다음 `D2` 응답을 받아서 |
| `D2` 폴링 | 기동 시 1회 정도 | 계속 (수백 ms 주기) |

C-2(폴링 주기)가 1차 단서가 되고, 아래 두 실험이 확정한다.

#### 실험 1 — `relay off` 후 버튼 누르기 (먼저 이것부터)

명령이 본체에 닿지 않게 막은 상태에서 램프만 본다.

1. `relay off`
2. PGM CH1 버튼을 누른다 (영상은 바뀌지 않는 것이 정상)
3. 램프를 관찰
4. `relay on` 으로 반드시 복구

| 관찰 | 판정 |
|---|---|
| CH1 램프가 켜짐 | **모델 A.** 본체와 무관하게 컨트롤러가 스스로 켠다 |
| 램프가 안 켜짐 | **모델 B.** 본체 회신을 기다린다 |
| 램프가 전부 꺼지거나 깜빡임 | 모델 B + 통신 두절 시 에러 표시. 그 동작도 기록해 둔다 |

#### 실험 2 — 가짜 응답 주입 (확증용)

아무 버튼도 누르지 않은 채, 컨트롤러에게 "PGM은 CH3야" 라고 거짓말한다.

1. `relay off` (컨트롤러의 폴링과 주입 프레임이 섞이지 않게)
2. `inject on`
3. `sendctrl AA D2 55 04 02` — PGM=CH3(`0x04`), PVW=CH2(`0x02`). 체크섬은 자동으로 `27` 이 붙는다
4. 램프를 관찰
5. `inject off` → `relay on` 으로 복구

| 관찰 | 판정 |
|---|---|
| CH3 램프가 켜짐 | **모델 B 확정.** 본체 회신이 램프를 몰아준다 |
| 아무 반응 없음 | 아래 주의사항을 보고 재시도. 그래도 없으면 모델 A |

> **주의.** 반응이 없다고 바로 모델 A로 단정하면 안 된다. 컨트롤러가 자기가 보낸
> `AB D2` 요청 **직후의 짧은 창** 에서만 응답을 받아들일 수 있기 때문이다.
> 이 경우 손으로 타이밍을 맞추기 어려우므로,
> ① 같은 명령을 연속으로 여러 번 보내 창에 걸리게 하거나,
> ② 그래도 안 되면 판정을 보류하고, 펌웨어에 **컨트롤러의 `AB D2` 요청을 감지해
> 자동으로 가짜 응답을 돌려주는 기능**을 임시로 넣어 다시 시도한다.

#### 확정 후 반영

- **모델 B** 로 확정되면, `D2` 응답 바이트는 곧 램프 패턴이다. 8채널에서는 CH1~CH8이
  bit0~bit7을 다 쓰므로 **OFF 비트가 들어갈 자리가 없다.** 즉 NMX-1108은 인코딩이
  반드시 바뀌었다는 뜻이고, 가장 유력한 후보는 지금 `0x55` 로 고정된 3번째 바이트다.
  B-3에서 CH7/CH8을 누를 때 그 자리도 같이 변하는지 반드시 확인한다.
- **모델 A** 로 확정되면, ESP32가 컨트롤러를 대체할 때 램프 상태를 스스로 관리해야 하고,
  본체와 어긋날 수 있으므로 주기적으로 `D2` 로 재동기하는 로직이 필요하다.

### [ ] D-2. EFFECT INV 인코딩 — **P2**

1106은 `0x01`~`0x08` 이 EFFECT 1~8, `0x11`~`0x18` 이 INV 1~8이다(상위 니블 = INV 플래그).

**테스트 조건**: EFFECT 1~8을 각각 정방향/INV로 선택.

### [ ] D-3. 송신 실험 — **P2** (A~C 완료 후에만)

> **주의.** 프로토콜을 확인하기 전에는 하지 않는다. `inject on` 을 거쳐야 송신된다.
> 중계 트래픽 사이에 임의 프레임이 끼어들므로, 컨트롤러가 폴링 중이면 충돌할 수 있다.

브리지 구조라 TX가 이미 양쪽에 연결돼 있어 배선을 바꿀 필요는 없다.

**테스트 조건**
1. `inject on` 입력
2. `sendmain AB D2 00 00 01` — 상태 조회부터 시도 (읽기 전용이라 가장 안전)
3. `[MAIN->CTRL] AA D2 ...` 응답이 오는지 확인
4. 응답이 확인되면 `sendmain AB 09 00 00 01` 로 PGM CH1 전환 시도
5. 끝나면 `inject off`

**판정**
- 상태 조회 응답이 오면 본체가 외부 명령을 받아들인다는 뜻 → B-3 검증에 활용 가능
- CH 전환이 실제로 먹으면 2차 목표(대체 컨트롤러) 진입 가능
- 응답이 없거나 믹서가 이상 동작 → 즉시 `inject off`. 컨트롤러 폴링과 충돌했을 수 있으니
  `relay off` 상태에서 다시 시도
