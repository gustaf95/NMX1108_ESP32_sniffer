# NMX-1108 미확인 항목 및 실측 계획

이 펌웨어의 프로토콜 해석은 **NMX-1106 문서**를 근거로 한 것이고, NMX-1108에서 확장·변경된
부분은 아직 추정이다. 추정 구간은 로그에 `?` 가 붙어 나오므로, 아래 항목을 실측해서 확정한다.

- 상태 표기: `[ ]` 미확인 / `[x]` 확정
- 우선순위: **P0** 다른 항목의 전제 / **P1** 8채널 확장 핵심 / **P2** 부가 확인
- 각 항목의 `기록:` 칸에 실제 관찰한 프레임을 적어 둔다.

> **이 문서는 패시브 탭(커플링) 방식 기준이다.**
> ESP32는 RX만 연결되어 **어떤 프레임도 송신할 수 없다.** 중계 제어(`relay`)나
> 프레임 주입(`inject`, `sendmain`, `sendctrl`)을 전제로 하던 항목은 전부 걷어냈고,
> 대신 관찰만으로 판정하는 절차로 바꿨다. 걷어낸 항목은 6절에 목록만 남겼다.

관련 파일: [README.md](README.md) · [../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) · [NMX-1106_통신 프로토콜.txt](NMX-1106_통신%20프로토콜.txt)

**진행 순서** — A-1(장비 없이) → A-6(무해성) → A-2(배선·방향) → A-3(통신 파라미터) →
나머지 A → B → C → D

### [ ] A-2. 탭 배선 및 방향 판정 — **P0**

브리지에서는 **믹서가 동작하는 것 자체가 배선이 맞다는 증거**였다.
탭에서는 배선을 틀려도 믹서가 멀쩡하므로 그 근거가 사라졌다.
대신 **바이트가 들어오는지**와 **방향 자동 판정이 확정되는지**로 본다.

**테스트 조건**
1. [README.md](README.md) 2절대로 탭을 연결한다 (RJ45 4·5·6번 → MAX3232 리시버 2개)
2. `pio device monitor` 후 `raw on` 으로 원시 바이트부터 본다
3. 컨트롤러에서 PGM CAM1 버튼을 여러 번 누른다
4. `dir` 로 방향 판정 상태를 확인한다

**판정**

| 관찰 | 해석 | 조치 |
|---|---|---|
| 두 포트 모두 바이트 유입 + `dir` 확정 + 버튼 누를 때 `[C>M] AB 09 00 00 01 4A` | 배선·방향 모두 정상 | 확정 |
| 버튼을 눌렀는데 `[M>C]` 로 찍힘 | 방향 라벨이 반대 | `dir swap`. **배선은 만지지 않는다** |
| 한 포트만 바이트 유입 | ① 탭선 하나가 안 물렸다 ② 그 방향은 원래 트래픽이 없다(C-1) | 먼저 버튼을 눌러 `[C>M]` 쪽이 살아 있는지 확인. `[M>C]` 만 없으면 C-1로 넘어간다 |
| **두 포트에 같은 프레임이 동시에** | 탭선 두 가닥이 **같은 신호선**에 물렸다 | RJ45 5번과 6번에 하나씩 갈렸는지 다시 확인 |
| 아무 바이트도 없음 | **GND 미연결이 1순위** | RJ45 4번(GND)이 MAX3232 GND·ESP32 GND와 공통인지 확인. 그 다음 MAX3232 VCC |
| 바이트는 들어오는데 `CHK=BAD` / `SKIP` 뿐 | 보레이트·형식 문제 | A-3 으로 |
| `dir` 이 확정 안 됨 (양쪽 다 같은 헤더 우세) | 같은 선 중복 탭 또는 트래픽 부족 | 버튼을 더 누르고, 그래도 안 되면 위 "같은 프레임" 항 확인 |

> 방향 판정은 **체크섬 OK 프레임 20개 이상 + 한쪽 헤더 80% 이상**에서 확정된다
> ([README.md](README.md) 4.2). 트래픽이 적으면 한동안 `[P1?]` 로 찍히는 것이 정상이다.

### [ ] A-3. 통신 파라미터 확정 — **P0**

문서에 `9600BPS, 1STOP` 만 있고 데이터 비트/패리티는 명시가 없어 `8N1` 로 가정했다.
**탭에서는 값을 아무리 틀리게 넣어도 장비에 영향이 없으므로 마음껏 시도한다.**
재빌드도 필요 없다.

**테스트 조건**
1. **스캔 중 트래픽이 있어야 하므로**, 컨트롤러 버튼을 계속 누르거나 페이더를 왕복시킨다
2. `scan` 실행 (보레이트만, 후보당 3초)
3. 결과가 안 나오면 `scan full` (보레이트 × 형식, 약 2분)

**판정**
- `9600 8N1` 에서 `chk-ok` 가 다수 → 문서 가정 확정
- 다른 조합에서 `chk-ok` 가 몰림 → 그 값을 채택(`apply`)하고
  [README.md](README.md) 1절의 기본값을 실측값으로 고친다
- 모든 후보에서 `chk-ok` = 0 인데 `frames` 만 잡힘 → 우연히 헤더 값이 나온 것. 무시
- 모든 후보에서 아무것도 안 잡힘 → 신호 자체가 안 들어오는 것. **A-2로 되돌아간다**
- 기대 프레임 `AB 09 00 00 01 4A` 와 한 바이트도 틀리지 않고 `CHK=OK` → 최종 확인

**기록:** 확정 보레이트 = ____ , 형식 = ____ , scan 최고점 = ____ chk-ok

### [ ] A-4. 프레임 길이 6바이트 고정 — **P1**

1106 문서의 예제는 전부 6바이트다. 1108에서 8채널용으로 길이가 늘어났을 수 있다.

**테스트 조건**
1. 버튼을 하나씩 천천히 누르며 10분 정도 로그를 받는다
2. `stats` 로 `incomplete` / `skipped bytes` / `chk BAD` 를 확인
3. `overflow` 도 함께 본다. 0이 아니면 아래 판정의 신뢰도가 떨어진다(A-5)

**판정**
- 세 값이 모두 0에 가까움 → 6바이트 고정 확정
- `skipped bytes` 나 `chk BAD` 가 프레임 수에 비례해서 늘어남 → **길이가 6이 아니다.**
  `raw on` 으로 전환해 헤더(`AB`) 사이의 실제 바이트 수를 세고
  [../include/nmx_protocol.h](../include/nmx_protocol.h) 의 `FRAME_LEN` 을 조정
- A-3을 통과했는데도 깨진다면 길이 쪽을 의심한다. 보레이트 문제라면 A-3의 `scan` 에서
  `chk-ok` 가 애초에 안 나왔을 것이다

### [ ] A-5. 수집 무결성 — **P0**

탭은 **놓친 바이트를 되돌려 받을 방법이 없다.** 장비는 멀쩡하지만 로그에 구멍이 나고,
그 구멍은 B·C 항목의 판정을 통째로 흔든다. 브리지의 `bytes == relayed` 를
**`overflow == 0`** 이 대신한다.

**테스트 조건**
1. `clear` 로 통계 초기화
2. 버튼을 빠르게 연타하고, 페이더도 빠르게 왕복시킨다 (트래픽을 일부러 몰아준다)
3. `raw on` 으로 로그량을 두 배로 늘린 뒤 2번을 반복
4. `stats` 를 여러 번 연속으로 쳐서 긴 출력이 나가는 중에도 유실이 없는지 본다

**판정**
- `overflow` = 0 (양방향 모두) → 유실 없음. 확정
- `overflow` > 0 → **그만큼 영영 놓쳤다.** `raw off` 로 로그량을 줄이고 재시도.
  그래도 계속되면 RX 버퍼를 키우거나 수집을 전용 태스크로 분리한다
  ([README.md](README.md) 18.1)
- `dropped log lines` 가 늘어남 → **정상 동작이다.** 화면 출력만 버린 것이고 수집은 살아 있다.
  다만 그만큼 관찰 기록이 비므로, 분석 중에는 `raw off` 로 로그량을 줄인다
- `overflow` 와 `dropped log lines` 를 헷갈리지 않는다. 앞은 **바이트 유실**,
  뒤는 **화면 출력 포기**다

### [ ] B-1. PGM CH7 / CH8 명령 프레임 — **P1**

**추정값**

```text
AB 09 00 00 07 44   PGM CH7
AB 09 00 00 08 43   PGM CH8
```

**테스트 조건**
1. PGM CH1 → CH2 → ... → CH8 순서로 하나씩 누른다 (각 1초 간격)
2. `[C>M]` 프레임을 순서대로 기록

- `PGM CH 7?` / `PGM CH 8?` 로 디코딩되면 추정 적중 →
  [../src/nmx_protocol.cpp](../src/nmx_protocol.cpp) 의 `describeChannelSelect()` 에서

- `CHK=BAD` 가 뜨면 체크섬 식이 확장 명령에서 다를 수 있다 → `expected CHK=` 값과 비교

### [ ] B-3. D2 응답의 CH7/CH8 표현 — **P1** (가장 불확실)

1106의 `D2` 응답은 **비트마스크**다. `0x01`=CH1 … `0x20`=CH6, 그리고 `0x40`=**OFF**.
8채널로 늘리면 CH7/CH8이 들어갈 자리가 `0x40`/`0x80` 인데 `0x40` 은 이미 OFF가 쓰고 있다.
즉 **OFF 코드가 바뀌었거나, CH7/CH8이 다른 방식으로 실린다.**

펌웨어는 이 모호함을 로그에 그대로 노출한다.

| 관찰값 | 로그 표기 |
|---|---|
| `0x40` | `OFF\|CH7?` |
| `0x80` | `CH8?` |
| `0x00` | `NONE` |

**테스트 조건**

본체가 `AB D2 00 00 01 81` 요청에 응답하는지부터 확인해야 한다(C-1 선행).
**탭에서는 요청을 대신 보낼 수 없으므로, 컨트롤러가 스스로 `D2` 를 물어봐 주기를 기다린다.**
C-1에서 요청-응답 쌍이 관찰되지 않으면 이 항목은 진행할 수 없다.

응답이 확인되면 아래 순서로 하나씩 바꾸며 `[M>C] AA D2 55 xx yy` 의
`xx`(PGM) / `yy`(PVW) 를 기록한다.

1. PGM CH1 선택 → 응답 기록
2. PGM CH6 선택 → 응답 기록
3. **PGM CH7 선택 → 응답 기록** ← 핵심
4. **PGM CH8 선택 → 응답 기록** ← 핵심
5. **PGM 전체 OFF → 응답 기록** ← 핵심
6. PVW 에 대해 1~5 반복

**판정**
- CH7에서 `0x40`, OFF에서 `0x40` 이 **아닌** 값 → CH7=`0x40`, CH8=`0x80`, OFF는 새 코드.
  `formatChannelMask()` 의 `CH_MASK_OFF` 분기를 새 OFF 코드로 교체
- CH7에서 `0x40` 이 아닌 값이 나옴 → 비트마스크가 아니거나 바이트가 하나 더 늘었다.
  `xx yy` 외의 바이트(특히 `0x55` 자리)도 같이 변하는지 확인
- OFF에서 `0x40` 유지 + CH7에서 다른 값 → 1106 규칙 그대로 + CH7/CH8만 별도 인코딩

> C-6과 함께 보면 해석이 빨라진다. 이 바이트가 **램프 패턴**이라면 8채널에서는
> bit0~bit7을 CH1~CH8이 다 쓰게 되어 OFF가 들어갈 자리가 없다. 그렇다면 `0x55` 자리가
> 확장 바이트로 쓰였을 가능성이 높으므로, `xx yy` 만 보지 말고 **3번째 바이트도 같이 기록**한다.

**기록:**

| 상태 | PGM 바이트 | PVW 바이트 | 3번째 바이트 |
|---|---|---|---|
| CH1 | | | |
| CH6 | | | |
| CH7 | | | |
| CH8 | | | |
| OFF | | | |

### [ ] B-4. D3 응답의 예약 비트 — **P2**

1106 문서에서 `BYTE_5` 의 bit4/bit5는 `Fixed 0` 이다. 1108에서 확장 플래그로 쓰였을 수 있다.
켜져 있으면 로그에 `(fixed-0 bits set: 0x..?)` 가 붙는다.

**테스트 조건**
1. EFFECT / CKEY / PIP / DSK / EXT AUDIO 를 하나씩 켜고 끄며 `AA D3` 응답을 기록
2. 어떤 조작에서도 안 변하는 비트가 있는지 대조

**판정**
- `fixed-0 bits set` 표시가 한 번도 안 뜸 → 1106과 동일. 확정
- 특정 조작에서 bit4/bit5가 켜짐 → 그 조작 이름을 디코더에 추가

## C. 동작 방식 및 기존 명령의 동일성

### [ ] C-1. 본체의 상태 조회 응답 여부 — **P1**

`AB D2 00 00 01 81` 요청에 NMX-1108 본체가 실제로 응답하는지 미확인. B-3의 전제다.

**테스트 조건**
1. 컨트롤러를 정상 연결한 상태로 로그를 받는다
2. `[C>M] ... AB D2 ...` 직후 `[M>C] ... AA D2 ...` 가 따라오는지 본다
3. 조작 없이 2분 방치했을 때도 요청이 나가는지 함께 본다 (C-2와 같이 관찰하면 된다)

**판정**
- 요청-응답 쌍이 보임 → 확정. B-3 진행 가능. 응답 지연도 기록해 둔다
- `[C>M]` 요청은 있는데 `[M>C]` 응답이 없음 → 본체가 상태 조회를 지원하지 않거나,
  포트2 탭선/GND 문제. **A-2를 먼저 다시 확인**한다
- **컨트롤러가 `D2` 요청 자체를 안 보냄** → 탭만으로는 더 진행할 수 없다.
  요청을 대신 넣어보는 실험은 6절 참조 (브리지 브랜치)
- `[M>C]` 에 바이트가 전혀 없음 → C-6의 모델 A를 강하게 시사한다. 그쪽도 같이 본다

**기록:** 요청 관찰 = ____ , 응답 관찰 = ____ , 응답 지연 = ____ ms

### [ ] C-2. 컨트롤러의 주기적 폴링 여부 — **P2**

컨트롤러가 상태를 주기적으로 물어보는지에 따라, 나중에 ESP32가 컨트롤러를 대체할 때
폴링 루프를 흉내내야 하는지가 갈린다. C-6의 1차 단서이기도 하다.

**테스트 조건**
1. 버튼을 **전혀 누르지 않은 상태**로 2분간 방치
2. `clear` 로 통계를 비운 뒤 다시 2분 방치하고 `stats`
3. `프레임 평균 간격` 항목을 읽는다 (수동 계산 불필요)

**판정**
- `frames` 가 계속 늘어남 → 주기적 폴링 있음. `프레임 평균 간격` 을 주기로 기록
- `frames` 가 0 → 이벤트 구동. 버튼을 눌렀을 때만 전송
- 폴링이 활발할수록 C-6의 **모델 B**(본체 회신으로 램프 점등)에 무게가 실린다

**기록:** 폴링 주기 = ____ ms , 방향 = ____

### [ ] C-3. TAKE / CUT / FADER 동일성 — **P2**

**추정값** (1106 기준)

```text
AB 06 00 00 01 4D   FADER MODE TAKE
AB 06 00 00 02 4C   FADER MODE CUT
AB 07 00 D2 D3 CHK  Manual Fader, 값 = (D2<<8)|D3, 0x000~0x1FF
```

**테스트 조건**
1. TAKE 버튼, CUT 버튼을 각각 누른다
2. 수동 페이더를 **한쪽 끝에서 반대쪽 끝까지 천천히** 민다

**판정**
- `FADER MODE TAKE` / `FADER MODE CUT` 이 그대로 나오면 확정
- 페이더 로그의 값이 `FADER 0x000` → `FADER 0x1FF` 로 단조 증가하면 16비트 해석 확정
- 값이 `0x1FF` 를 넘거나 중간에 튀면 스케일이 다르다 → 실측 최대/최소를 기록
- 값이 중간중간 건너뛰면 **유실을 의심한다.** `stats` 의 `overflow` 를 먼저 본다(A-5).
  페이더는 트래픽이 가장 몰리는 조작이라 유실이 여기서 먼저 드러난다

**기록:** 페이더 최소 = ____ , 최대 = ____ , overflow = ____

### [ ] C-5. 미해독 CMD 수집 — **P2**

1108 전용 버튼(있다면)은 문서에 없는 CMD를 쓸 수 있다.
**탭 방식은 실사용 장비에 오래 붙여둘 수 있으므로**, 실제 운용 중에 나오는 명령까지 모을 수 있다.

**테스트 조건**
1. `clear` 후, 컨트롤러의 **모든 버튼·노브를 하나씩** 조작
2. `stats` 의 `unknown cmd` 와 CMD 히스토그램을 확인
3. 가능하면 실제 운용 중에 장시간 붙여두고 다시 확인

- `unknown cmd` 가 0 → 1106 명령 집합으로 전부 커버됨

### [ ] C-6. 컨트롤러 램프를 누가 켜는가 — **P1** (탭에서는 부분 확정)

버튼을 누르면 컨트롤러의 해당 램프에 불이 들어온다. 이것이 **컨트롤러가 스스로 켜는 것**인지,
**본체 회신을 받아서 켜는 것**인지 확정한다. 나중에 ESP32가 컨트롤러를 대체하거나
네트워크로 제어할 때 어느 쪽을 흉내내야 하는지가 여기서 갈린다.

**프로토콜에서 읽히는 정황** (본체가 몰아주는 쪽에 무게)

같은 CH3인데 명령과 응답의 인코딩이 다르다.

```text
명령  AB 09 00 00 03 48     ← 채널 번호 3 (그냥 숫자)
응답  AA D2 55 04 ..        ← 0x04 (비트마스크, bit2)
```

PGM은 한 번에 한 채널만 켜지므로 비트마스크일 이유가 없는데도 비트로 펼쳐져 있다.
게다가 비트 배치가 패널 버튼 수와 정확히 맞는다.

```text
bit0 CH1 / bit1 CH2 / bit2 CH3 / bit3 CH4 / bit4 CH5 / bit5 CH6 / bit6 OFF   = 7개 버튼 7비트
```

`0x40 = OFF` 가 **전용 비트**라는 점이 특히 그렇다. 순수한 상태값이라면 OFF는 `0x00` 이면
충분하다. 명령표에 `AB 09 00 00 00 4B PGM CH OFF` 가 있으니 패널에 OFF 버튼이 실재하고,
그렇다면 이 바이트는 **램프 패턴 그 자체**로 보인다.

반대로, 문서에는 **자발적(unsolicited) 응답 프레임이 없다.** 모든 `AA` 는 `AB D2`/`AB D3`
요청에 대한 "Return Value" 로만 나온다. 따라서 가능한 모델은 두 가지다.

| | 모델 A — 로컬 점등 | 모델 B — 폴링 후 점등 |
|---|---|---|
| 버튼 누름 | 컨트롤러가 즉시 자기 램프 점등 | 명령만 보냄 |
| 램프 갱신 | 로컬 | 다음 `D2` 응답을 받아서 |
| `D2` 폴링 | 기동 시 1회 정도 | 계속 (수백 ms 주기) |

> **탭으로 어디까지 답이 나오는가.**
> **모델 A는 관찰만으로 확정할 수 있다.** 본체 회신이 아예 없는데 램프가 켜지면
> 컨트롤러가 스스로 켠 것 외에 설명이 없기 때문이다.
> **모델 B는 정황까지만 나온다.** 응답이 오고 램프가 켜지는 것을 봐도 인과가 아니라
> 순서일 뿐이다. 확증하려면 가짜 응답을 넣어 봐야 하고, 그건 송신이 필요하다(6절).

#### 관찰 1 — 본체 회신이 있는가 (먼저 이것부터)

1. `clear` 후 PGM CH1 버튼을 누른다
2. `[C>M]` 명령 직후 `[M>C]` 프레임이 따라오는지, 타임스탬프와 함께 본다

| 관찰 | 판정 |
|---|---|
| `[M>C]` 트래픽이 **전혀 없는데** 램프가 켜짐 | **모델 A 확정.** 여기서 끝난다 |
| `[M>C] AA D2` 가 오고 그 뒤에 램프가 켜짐 | 모델 B **유력**. 관찰 2로 |
| `[M>C]` 는 오는데 램프가 그보다 **먼저** 켜짐 | **모델 A 유력.** 회신은 무관한 폴링 응답일 수 있다 |

#### 관찰 2 — 램프 점등 시점과 응답 프레임의 선후

램프가 켜지는 순간을 눈으로 보면서 로그 타임스탬프와 대조한다.
사람 눈으로 수십 ms를 가르기는 어려우므로, 판정이 애매하면 아래를 쓴다.

- **폴링 주기를 이용한다.** C-2에서 폴링 주기가 길게 나왔다면(예: 500ms 이상),
  버튼을 누른 뒤 램프가 그 주기만큼 늦게 켜지는지 본다.
  **눈에 띄는 지연이 있으면 모델 B**, 즉각적이면 모델 A다.
- 스마트폰으로 패널과 화면을 한 프레임에 담아 슬로우모션 촬영하면 더 확실하다.

#### 관찰 3 — 케이블을 뽑고 버튼 누르기 (선택, 주의)

브리지의 `relay off` 실험을 손으로 하는 것과 같다. **탭이 아니라 원래 케이블을 뽑는다.**

> **실사용 중인 장비에서는 하지 않는다.** 통신이 실제로 끊긴다.
> 이 항목만은 탭 방식의 "장비를 건드리지 않는다"는 전제를 깬다.

1. 컨트롤러-본체 RJ45 케이블을 뽑는다
2. PGM CH1 버튼을 누른다 (영상은 바뀌지 않는 것이 정상)
3. 램프를 관찰한다
4. 케이블을 다시 꽂고 정상 복귀를 확인한다

| 관찰 | 판정 |
|---|---|
| CH1 램프가 켜짐 | **모델 A 확정** |
| 램프가 안 켜짐 | **모델 B 확정** |
| 램프가 전부 꺼지거나 깜빡임 | 모델 B + 통신 두절 시 에러 표시. 그 동작도 기록해 둔다 |

#### 확정 후 반영

- **모델 B** 로 확정되면, `D2` 응답 바이트는 곧 램프 패턴이다. 8채널에서는 CH1~CH8이
  bit0~bit7을 다 쓰므로 **OFF 비트가 들어갈 자리가 없다.** 즉 NMX-1108은 인코딩이
  반드시 바뀌었다는 뜻이고, 가장 유력한 후보는 지금 `0x55` 로 고정된 3번째 바이트다.
  B-3에서 CH7/CH8을 누를 때 그 자리도 같이 변하는지 반드시 확인한다.
- **모델 A** 로 확정되면, ESP32가 컨트롤러를 대체할 때 램프 상태를 스스로 관리해야 하고,
  본체와 어긋날 수 있으므로 주기적으로 `D2` 로 재동기하는 로직이 필요하다.

### [ ] D-1. SETUP 방향키 라벨 — **P2**

원문 문서의 한글이 깨져 있어 `0x00` / `0x01` 을 UP/DOWN으로 **추정**했다.

## F. 이 브랜치에서 할 수 없는 것

송신이 필요해 **패시브 탭으로는 수행 불가능**한 항목이다. 절차는 삭제했고,
프로토콜이 확정된 뒤 브리지 브랜치에서 **실사용이 아닌 장비**로 진행한다.

| 항목 | 내용 | 대체 |
|---|---|---|
| C-6 가짜 응답 주입 | `sendctrl AA D2 55 04 02` 로 컨트롤러에 거짓 상태를 넣어 램프 반응을 본다. 모델 B의 **유일한 확증 수단** | C-6 관찰 1~3으로 모델 A는 확정 가능, 모델 B는 정황까지 |
| 본체 상태 조회 직접 요청 | 컨트롤러가 `D2` 를 안 보낼 때 `sendmain AB D2 00 00 01` 로 대신 물어본다 | 없음. C-1이 막히면 B-3도 막힌다 |
| 송신 실험 전반 | 본체가 외부 명령을 받아들이는지, CH 전환이 실제로 먹는지 | 없음. 대체 컨트롤러 진입 조건이므로 브리지 전환 시 최우선 |

**진행이 막히는 지점은 하나다.** C-1에서 컨트롤러가 `D2` 요청을 아예 안 보내면
B-3(가장 불확실한 항목)을 관찰만으로 풀 수 없다. 그 경우 B-3만 브리지 브랜치로 넘긴다.
